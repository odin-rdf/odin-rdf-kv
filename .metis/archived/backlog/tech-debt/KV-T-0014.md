# Place the free-list run in a fragmented free pool

## Objective

Stop the free list's own run from extending the file when there are plenty of free pages but no contiguous run of exactly the length needed.

## Backlog Item Details

### Type
- [x] Tech Debt - Code improvement or refactoring

### Priority
- [x] P2 - Medium (nice to have)

### Technical Debt Impact
- **Current problems:**
  - A run must be exactly `overflow_pages(16 × count)` long, because open validates it that way. `freelist_place` (`kv/freelist.odin`) therefore needs a free run of exactly the right length, and falls back to extending the file if there isn't one.
  - KV-T-0013 measured this: after a long reader ends, a free list of about 7,500 records (a 30-page run) extended the file 0–3 times per 1,000 commits, by 29–90 pages each time.
  - A scattered 10⁵-record list extended the file by its whole 396-page run.
- **Benefits of fixing:** the file stops growing once the free pool is large but fragmented, which completes NFR-004 for workloads that follow a long reader.
- **Risk assessment:** low for now. The growth is bounded and rare, but it gets worse as fragmentation grows, which delete (step 4) will add to.

## Acceptance Criteria

- [x] Choose among the options with a measurement:
  - accept a run longer than its records need (relax the validation at open to `overflow_count ≥ needed`, with the slack zeroed);
  - best-fit placement, or placement from the top of the pool;
  - chain the run's pages;
  - extent records (see KV-I-0002 Alternatives).
- [x] KV-T-0013's long-reader test runs with no file growth after the reader ends, on every seed.
- [x] `space_check`, the validation tests and the build matrix still pass.

## Implementation Notes

The evidence is in KV-T-0013's Status Updates and KV-I-0002's Results (known limitations). Relaxing the validation is the smallest change, and it stays compatible: files written today have exact runs, which still satisfy `≥`.

## Status Updates

### 2026-09-24: done, by allowing the run one page of slack

**Measurement: the cause was exact length, not contiguity.** I added temporary logging to `freelist_place` and ran the long-reader test on seeds 1–16 at `-o:speed`. Each time placement fell back to the end of the file, the logging recorded whether no length fitted exactly or no free run of that length existed. It also recorded whether a run one page longer was free.
- Every one of the 7 fallbacks after the reader ended (seeds 1, 6, 7, 16) was **no exact fit**, with 7,100–7,400 pages reusable, and in every one a run of the relaxed length was free. Record counts were 7,196 and 7,453: 257 × 28 and 257 × 29, as the analysis below predicts.
- The other fallbacks happened while the reader was held, with 1–2 reusable pages. They are expected, and nothing can place a run there.

*Why no exact fit can exist:* taking j pages leaves n − j records, and the length they need falls by one page per page's worth of records (256 at 4 KiB). As j grows, the needed length can jump from j + 1 straight to j − 1. That happens exactly when n − j = 256·j, so n = 257·j at 4 KiB. For a ~30-page run it hits about one commit in 256, which matches the 0–3 fallbacks per 1,000 commits KV-T-0013 saw.

**Decision: the smallest option, relaxing the validation, bounded to one page.** Best-fit or top-of-pool placement would not help, because the problem is the length and not where the run goes. Chained pages and extent records are format changes that address contiguity, which this workload doesn't hit.
- `freelist_place` takes the **shortest** j whose records need at most j pages. That j has at most one page of slack: j − 1 pages were too few, so the n − j + 1 records they would leave need at least j pages, and one record fewer needs at least j − 1. The proof is in the doc comment.
- **Deviation from the task text:** the task proposed `overflow_count ≥ needed`. The check at open is `needed ≤ overflow_count ≤ needed + FREELIST_RUN_SLACK` (1) instead. With no upper bound, a corrupt header counting extra pages would make the next commit free pages the tree still uses. The bound keeps what the exact check guaranteed, except for one page. `run_header_check` takes a `slack` argument, 0 for overflow values.
- **The length of the previous run comes from its header now,** not from `freelist_run_pages(count)`. `freelist_build` reads `overflow_count` through `page_ptr`. Otherwise the slack page would leak, and `space_check` catches that ("page owned by nothing").
- The slack is zeroed. `freelist_write` already zeroed everything after the last record.
- `meta_read`'s range check in `env.odin` stays at the needed length. It is a lower bound, and the header check does the rest.
- **Compatibility:** files written before this have exact runs, which pass the new check. A binary from before this change reports `Corrupted` on a file with a slack page. I didn't bump `VERSION`, because there are no deployed files.

**Tests:**
- `freelist_run_len` (in `tests/tree_helpers.odin`) reads a run's length from its header. Five call sites that computed it from the record count use it now.
- `read_freelist` accepts `needed` or `needed + 1`.
- `test_freelist_run_length_fits_its_records`: the 257-record case now places a 2-page run with a page of slack in reusable pages. A new case gives the same records with no two reusable pages consecutive, so the run still extends the file. For every case the test also checks that the next commit frees every page of the run.
- New `test_freelist_load_accepts_a_page_of_slack`. In the bad-lists test, "header page count" is now "too many", using 2 pages of slack.
- The long-reader test asserts `growth == 0`, where it allowed up to five runs.

**Checked against deliberate bugs:**
- Freeing the old run by its record count: "run page 4 was not freed", and `space_check` fails in the long reader ("page owned by nothing").
- No slack at open: the new load test fails, the reopen gets `Corrupted`, and `space_check` in the long reader reports "bad free-list run".
- Exact fit in placement: the 257-record case extends the file, and the long reader grows by 29 pages on seed 1.

**Results:**
- Long reader, seeds 1–16 at `-o:speed`: **0 pages of growth on every seed.** Before, seeds 1, 6, 7 and 16 grew by 29, 29, 90 and 60 pages. More than 10,900 pages were reused on each seed.
- The free-list cost benchmark is unchanged, except that the scattered 10⁵ layout still extends the file by its whole 396-page run. In that layout no two free pages are consecutive, so no contiguous run of any length exists. Only chained run pages or extent records would help, and it takes a long reader on a large database to get there. It stays a known limitation, not filed.
- `scripts/test.sh`: 108/108 in debug, `-o:speed` and ASan, and `odin check` is clean for the four targets.
