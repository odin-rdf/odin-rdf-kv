# Reader table

## Parent Initiative

[[KV-I-0002]]

## Objective

Track which snapshots live read transactions hold, so a writer can compute the oldest one still in use (KV-I-0002 REQ-001, decision D2). Nothing uses it for reuse yet; KV-T-0012 does.

## Acceptance Criteria

- [x] `Env.readers` is a sorted `[dynamic]Reader_Slot{txn_id: Txn_Id, count: int}`, guarded by `snapshot_mutex`, with capacity reserved at `env_open` and freed at `env_close`.
- [x] `txn_begin(ro)` registers under the lock that copies the snapshot. It increments the last slot if it holds the same `txn_id`, and appends a slot otherwise. It asserts that snapshots only increase.
- [x] `txn_abort` (and so `txn_commit`) of a read transaction deregisters: binary search for the slot, decrement it, and remove it at zero. A write transaction never registers.
- [x] A private `oldest_reader(env) -> (Txn_Id, bool)` (caller holds the lock) returns `readers[0]`. There's also an exported test hook, or a field that tests can read.
- [x] In debug builds, `env_close` asserts the table is empty, alongside the existing `active_txns` check.
- [x] NFR-001: once the table's capacity is reached it allocates nothing more. A tracking-allocator test shows that repeated `txn_begin(ro)`/`txn_abort` pairs allocate nothing.
- [x] Tests:
  - many readers on one snapshot;
  - readers on several snapshots ended out of order, with `oldest` correct after each step;
  - a threaded test with readers beginning and ending while a writer commits, where the table ends empty and never has a slot at count 0 (run with `-sanitize:thread`).
- [x] Deliberate-bug check: skip the deregistration, or remove the wrong slot, and a test fails. Record it here.
- [x] `scripts/test.sh` passes.

## Implementation Notes

### Technical Approach
- The slots use `env.allocator`, not the caller's context allocator, because readers run on arbitrary threads. Reserve 16 at open.
- Removing a slot is `ordered_remove`, and it's O(live snapshots), which is tiny. The common case removes slot 0 or the last slot.
- `Txn` is a value that moves, so deregistration uses `txn.snapshot.txn_id` as its key. It must not store a slot index, because indices shift on removal.
- Update the comment in `txn_begin` that promises this step.

### Dependencies
None. This is the first task of KV-I-0002.

### Risk Considerations
- A read transaction that is never ended pins its slot forever. That's the documented caveat, and `env_close`'s debug assert catches it in tests.
- Growing the array while holding `snapshot_mutex` makes an allocation happen under the lock. It's rare, and acceptable (NFR-002 bounds the work, not allocations).

## Status Updates

### 2026-09-24: implemented

**What was built**
- `kv/env.odin`: `Reader_Slot{txn_id, count}`, `READER_TABLE_CAPACITY :: 16`, and `Env.readers` (guarded by `snapshot_mutex`, reserved in `env_open` with `env.allocator`, freed in `env_close`). Private `reader_register`, `reader_deregister` and `oldest_reader` (all with the lock held by the caller), and the exported test hook `env_oldest_reader(env)`, which takes the lock. `Env.readers` is also a plain field, so tests read it directly under `snapshot_mutex`.
- `kv/txn.odin`: `txn_begin` registers a read transaction under the lock that copies the snapshot, and `txn_abort` (and so `txn_commit`) deregisters one by `txn.snapshot.txn_id`. The step-5 promise comment is replaced. The key is `txn.read_only`, not `txn.write == nil`.
- `env_close` asserts in debug builds that the table is empty, next to the `active_txns` check.
- `tests/reader_test.odin` (new), four tests:
  - `test_reader_table_one_snapshot`: 100 readers on one snapshot, ended in random order through commit, abort and a repeated abort. It also checks that write transactions never register.
  - `test_reader_table_several_snapshots`: 2–4 readers on each of 30 snapshots (so the table grows past 16), ended in random order. After every step the whole table is compared against the expected slots, and `oldest` is checked.
  - `test_reader_table_allocates_nothing`: the env is opened with a tracking allocator. Begin/abort pairs allocate nothing, both within the reserved capacity and after the table grows to 32 slots (including ending the held readers out of order). After `env_close` nothing is left allocated and there are no bad frees.
  - `test_reader_table_across_threads`: 6 reader threads begin and end transactions, sometimes holding a second, newer one and ending the older one first, while the writer commits 300 times. After each commit and inside the readers, the table is checked for strictly increasing slots, no count ≤ 0, and no slot newer than the snapshot. Each reader also checks that `oldest ≤` its own snapshot. The table ends empty.

**Decisions**
- `env_open` returns `Out_Of_Memory` if reserving the table (or allocating the `Env`) fails; before, the result of `new(Env)` wasn't checked. The comment on `Error.Out_Of_Memory` now covers this.
- `txn_begin(ro)` returns `Out_Of_Memory` if growing the table fails. It unlocks and returns before touching `active_txns`, so a failed begin leaves nothing to end.
- `reader_register` asserts `last.txn_id <= txn_id` (snapshots only increase), and `reader_deregister` asserts that the slot exists. Both use plain `assert`, so they are active in every build except `-disable-assert`.

**Verification**
- `scripts/test.sh` passes: 83/83 tests in debug, `-o:speed` and `-sanitize:address`, plus `odin check` for darwin/linux × arm64/amd64.
- `-sanitize:thread` (debug, macOS arm64): the whole suite, 83/83, with no ThreadSanitizer reports. The threaded test ran about 0.5 M read transactions across 300 commits under TSan (1.5 M without it).

**Deliberate-bug checks** (each restored afterwards)
1. *Skip deregistration* in `txn_abort`: `one_snapshot` fails (count stays at 100), and `env_close`'s debug assert fires.
2. *Remove the wrong slot* (always slot 0): `several_snapshots` fails with a table mismatch and the wrong oldest reader, then trips the "not registered" assert. `allocates_nothing` fails on the same assert.
3. *Decrement the wrong slot* (always the last): `several_snapshots` and `allocates_nothing` fail. `one_snapshot` passes, as expected with only one slot.
4. *Always append a slot* (no shared slot per snapshot): all four tests fail, including "slots not strictly increasing" from the reader threads and an extra allocation in `allocates_nothing`.
5. *Write transactions register too*: all four fail.
6. *Register outside `snapshot_mutex`*: TSan reports a data race in `reader_register` from two reader threads in `test_reader_table_across_threads`.

**Open concern**
- In the threaded test, a table bug that trips one of `kv`'s asserts on a reader thread (checks 2 and 3) doesn't fail cleanly. The assert is printed, then the test binary hangs at 100% CPU and ignores SIGTERM. The Odin test runner only recovers panics on the test's own thread, and the panicking thread may hold `snapshot_mutex`. The single-threaded tests catch these bugs first, so this only affects diagnosis. The existing isolation test has the same property.
