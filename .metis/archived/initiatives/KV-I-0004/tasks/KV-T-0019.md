# Measure eviction and residency on macOS and Linux

## Parent Initiative

[[KV-I-0004]]

## Objective

Find out, on the real platforms, what the memory budget's mechanisms actually do before anything is built on them (KV-I-0004 D12). The vision says macOS eviction and `mincore` semantics *need to be verified empirically*, and review found that `core:mem/virtual`'s `decommit` uses the lazy `MADV_FREE`. The results decide the eviction method (D9), the OS check (D10) and how the dirty pool releases memory (D1).

## Acceptance Criteria

- [x] A test-only measurement (under `tests/`, registered only with a define such as `-define:KV_PLATFORM=true`), not code in `kv/`.
- [x] **File mapping, read-only `MAP_SHARED`, `MADV_RANDOM`:** touch ranges, then evict with each candidate, and record the process's resident size and what each method reports after each step:
  - macOS: `MADV_DONTNEED`, `MAP_FIXED` remap of the same file range, `msync(MS_INVALIDATE)` if it has any effect;
  - Linux: `MADV_DONTNEED` (and, for the record, `MADV_PAGEOUT`).
- [x] **What each residency source reports** for the same ranges: `mincore`, `/proc/self/pagemap` present bits (Linux), the per-region resident count (`mach_vm_region` on macOS, `/proc/self/smaps` on Linux) and process RSS. In particular whether macOS `mincore` counts page-cache pages that aren't mapped into the process (the vision expects it to overcount).
- [x] **Remap under load (macOS):** reader threads read the range continuously while another remaps it with `MAP_FIXED`, for long enough to trust: no fault, no wrong byte, and addresses stay valid. Run under TSan too.
- [x] **Anonymous memory release (D1):** resident size after committing and writing a 4 MiB region, then `MADV_FREE`, `MADV_DONTNEED`, `MADV_FREE_REUSABLE` (macOS) and an anonymous `MAP_FIXED` remap. Which drop the resident size at once.
- [x] The cost of each eviction and release call per chunk (256 KiB and 64 KiB), and of a refault from the page cache.
- [x] Results recorded in this task's Status Updates, with platform and OS versions. D1, D9 and D10 in KV-I-0004 are amended if they disagree, with a note saying what moved.
- [x] Run on macOS arm64 and in the Linux containers (arm64, amd64). Note where container results may differ from bare metal.

## Implementation Notes

### Technical Approach
- A standalone test file with its own small `mmap`/`madvise` wrappers; `kv/os_*.odin` doesn't change in this task.
- Resident size: macOS `task_info(TASK_VM_INFO)` (`resident_size`, and `phys_footprint` for the anonymous case); Linux `/proc/self/statm` or `smaps_rollup`, and the mapping's own entry in `/proc/self/smaps` for a per-range figure.
- Use a file of about 64 MiB so the numbers stand out from noise, and read it once first so it's in the page cache.

### Dependencies
None. First task of KV-I-0004, and it can run alongside KV-T-0020.

### Risk Considerations
- If no macOS method lowers the resident size of a shared file mapping, eviction on macOS falls back to the least bad method and the budget is Linux-only in practice. Production is Linux; macOS is the development platform. Record that plainly if it happens.
- Container results on Linux can differ from bare metal (cgroup accounting). The present bits and RSS are per process, so they should not.

## Status Updates

### 2026-09-24: measured on macOS and Linux; D10's macOS source needs a decision

**What was built** (tests only; `kv/` unchanged):
- `tests/platform_test.odin`: the measurement, with its own `madvise`/`mincore` bindings and `mmap` through `core:sys/posix`. Two tests, registered only with `-define:KV_PLATFORM=true`: `test_platform_residency` (file eviction and residency sources, anonymous release, costs per chunk) and `test_platform_remap_under_load`. Resident sizes are process-wide, so run them alone:
  `odin test tests -o:speed -define:KV_PLATFORM=true -define:ODIN_TEST_THREADS=1 -define:ODIN_TEST_NAMES=kv_tests.test_platform_residency,kv_tests.test_platform_remap_under_load`
- `tests/platform_darwin_test.odin` (`task_info(TASK_VM_INFO)` for `resident_size` and `phys_footprint`, `mach_vm_region(VM_REGION_EXTENDED_INFO)` summed over the regions in the range) and `tests/platform_linux_test.odin` (`/proc/self/pagemap` present bits, `Rss` of the mappings in `/proc/self/smaps`, `/proc/self/statm`, `RssAnon`).
- `scripts/test-linux.sh` passes extra arguments to `odin test`, like `scripts/test.sh` (`scripts/test-linux.sh arm64 -define:KV_PLATFORM=true …`).

**Platforms:**
- macOS 26.5.2 (25F84), Apple M4, 24 GiB, 16 KiB pages.
- Linux: OrbStack's VM, kernel 7.0.14-orbstack, Ubuntu 24.04.5 container (glibc 2.39), 4 KiB pages, 12 GiB. arm64 native; amd64 is emulated user code on the same arm64 kernel, so its syscall behaviour is the arm64 kernel's and only its costs are its own. amd64 agreed with arm64 on every residency figure. Not measured on bare metal. Everything measured here is per process (page tables, `pagemap`, RSS), which a container doesn't change; cgroup accounting was not measured.
- All figures from `-o:speed` runs (the debug runs agreed on every residency figure).

**File mapping** (64 MiB file, synced, in the page cache; mapped read-only, `MAP_SHARED`, `MADV_RANDOM`; touched 0–32 MiB, then evicted 0–16 MiB). MiB after the eviction; "cache" is what `mincore` reports, "RSS" the process's resident size above the baseline. Before any touch, both platforms reported mincore 64, and macOS region 64.

| method | macOS RSS | macOS mincore / region | Linux present / smaps / RSS | Linux mincore |
|---|---|---|---|---|
| none (after touch) | 32 | 64 / 64 | 32 / 32 / 32.4 | 64 |
| `MADV_DONTNEED` | **32** (no effect) | 64 / 64 | **16 / 16 / 16.7** | 64 |
| `posix_madvise(POSIX_MADV_DONTNEED)` | 32 | 64 / 64 | 32 / 32 / 32.6 (glibc: no-op) | 64 |
| `MADV_PAGEOUT` | n/a | n/a | 16 / 16 / 16.7 | **48** (page cache dropped) |
| `MAP_FIXED` remap | **16** | 64 / 64 | 16 / 16 / 16.7 | 64 |
| `msync(MS_INVALIDATE)` | 16 | **48 / 48** (page cache dropped) | 32 / 32 / 32.7 (no effect) | 64 |

- Every method left the range reading the file's bytes; nothing changed 100 ms later; re-reading the range restored 32 MiB on both.
- **macOS:** only the remap lowers the resident size while keeping the page cache. `MADV_DONTNEED` is a hint that does nothing measurable here (its only trace is a refault-like cost on the next touch: arm64 access-flag faults, the pages stay mapped). `MS_INVALIDATE` does lower the RSS, but it throws the pages out of the page cache for every process, and refaulting 256 KiB then costs ~450 µs (from the SSD) against ~5 µs.
- **Linux:** `MADV_DONTNEED` and the remap both work and leave the page cache; `MADV_PAGEOUT` also drops the cache (the reason it was rejected). **`posix_madvise(POSIX_MADV_DONTNEED)` is a no-op under glibc**, so eviction must call `madvise` itself; `kv/os_posix.odin`'s `os_advise_random` uses `posix_madvise`, which is fine for `RANDOM` only.
- **One touch brings in more than one page on Linux:** 64 one-byte touches, one per 256 KiB, added 64 × 64 KiB (present +3.9–4.0 MiB): file fault-around (`fault_around_bytes`, 64 KiB) maps 16 pages per fault despite `MADV_RANDOM`. The window is aligned to 64 KiB, so with D7's chunks (at least 64 KiB, aligned) it never crosses a chunk and the per-chunk estimate stays right. macOS maps exactly one 16 KiB page per fault (+1.0 MiB).

**Residency sources.**
- **Linux:** `pagemap` present bits and `smaps` Rss agree exactly with each other and with the RSS change, for every method. **`mincore` reports the page cache**: 64 MiB for a mapping nothing had touched. D10's Linux choice (pagemap, never mincore) holds.
- **macOS: no per-range source reports what is mapped into the process.** `mincore` and `mach_vm_region`'s `pages_resident` both count the file's pages in the page cache: 64 MiB before any touch, and unchanged by a remap that took the RSS from 32 to 16 MiB. So "errs only toward overcounting" is technically true of both, but the overcount is the whole cached file, which makes either useless for checking the estimate. Also probed with a throwaway test, and no better: `mincore`'s `MINCORE_REFERENCED` bit and `mach_vm_page_range_query`'s `VM_PAGE_QUERY_PAGE_REF` are set by touching and stay set after the remap (they're per physical page, not per mapping); `mach_vm_region_recurse` (`vm_region_submap_info_64`) reports the same object-resident count as the extended info. The only figure that follows the mapping is the **process-wide** `task_info` `resident_size`.
- Cost over the 64 MiB map (all per call): Linux arm64 pagemap 92 µs, smaps 231 µs (whole process), statm 3.3 µs, mincore 170 µs; macOS mincore 896 µs, mach_vm_region 28 µs, task_info 0.7 µs.

**Eviction under load** (4 reader threads reading random words and checking them, the main thread evicting random 256 KiB chunks as fast as it can, 10 s per method): no fault, no wrong word, no failed call, on every platform.

**Anonymous release** (4 MiB private anonymous, every page written, then released; KiB above the baseline, measured at once; nothing changed 100 ms later; every method left the range writable).

| method | macOS RSS / phys_footprint | Linux RSS / RssAnon / present | reads zero after |
|---|---|---|---|
| written | 4096 / 4112 | 4272 / 4276 / 4096 | |
| `MADV_FREE` | 4112 / 4112 (no drop) | 4352 / 4352 / 4096 (no drop) | no |
| `MADV_DONTNEED` | 4096 / 4112 (no drop) | **244 / 260 / 0** | Linux yes, macOS no |
| `MADV_FREE_REUSABLE` | 4096 / **16** | n/a | no |
| `MAP_FIXED` anonymous remap | **0 / 0** | **256 / 256 / 0** | yes |
| `virtual.decommit` (`mprotect(NONE)` + `MADV_FREE`) | 16 / 16 | 4368 / 4368 / 4096 (no drop) | no |

(Linux RSS carries ~250 KiB of the measurement's own temporary allocations.) `MADV_FREE_REUSABLE` lowers `phys_footprint` (what Activity Monitor and jetsam go by) but not `resident_size`. `virtual.decommit` does drop both on macOS, apparently through its `mprotect`, but not on Linux, where it is lazy exactly as review found.

**Costs per chunk**, µs, median (means within 10–20% except where noted). File: evicting a fully resident chunk, then touching every page of it again (a refault from the page cache). Anonymous: releasing a written chunk, then writing every page again (including `MADV_FREE_REUSE` or `commit` where the method needs it).

| call | macOS 256 KiB | macOS 64 KiB | Linux arm64 256 KiB | Linux arm64 64 KiB | Linux amd64 256 KiB | Linux amd64 64 KiB |
|---|---|---|---|---|---|---|
| file `MADV_DONTNEED` | 1.04 (no eviction) | 0.50 | 3.38 | 1.04 | 5.92 | 1.71 |
| file remap | 1.75 | 1.46 | 3.62 | 1.79 | 6.67 | 2.83 |
| file `MADV_PAGEOUT` | n/a | n/a | 25.4 | 6.17 | 37.3 | 10.6 |
| file `MS_INVALIDATE` | 6.33 | 1.29 | 0.21 (no-op) | 0.25 | 0.21 | 0.21 |
| refault after remap | 4.92 | 1.38 | 4.67 | 1.33 | 5.83 | 1.54 |
| refault after `MADV_DONTNEED` | 6.08 (mapped; access faults) | 1.62 | 5.25 | 1.29 | 7.12 | 1.46 |
| refault after `MADV_PAGEOUT` / `MS_INVALIDATE` (disk) | 447 | 67 (mean 109) | 146 | 36.1 | 174 | 39.0 |
| anon `MADV_DONTNEED` | 1.00 | 0.50 | 2.08 | 0.92 | 4.08 | 1.42 |
| anon remap | 2.21 | 0.96 | 2.67 | 1.38 | 4.92 | 2.21 |
| anon `MADV_FREE_REUSABLE` | 1.00 | 0.54 | n/a | n/a | n/a | n/a |

So evicting a 256 KiB chunk costs 2–7 µs and faulting it back from the page cache about as much; the rejected methods that drop the page cache cost 30–90× that on the refault.

**Decisions and what moved** (amended in KV-I-0004 with dated notes):
- **D9 holds as written.** macOS: `MAP_FIXED` remap of the same file range (only method that lowers RSS and keeps the page cache; safe under concurrent readers, TSan clean). Linux: `MADV_DONTNEED`, called through `madvise`, not `posix_madvise`. Added to D9: the glibc no-op, `MS_INVALIDATE` dropping the page cache on macOS, and fault-around (64 KiB per fault on Linux, within one chunk).
- **D1 settled on the remap for macOS.** `MADV_FREE_REUSABLE` lowers `phys_footprint` only, not `resident_size`; the anonymous `MAP_FIXED` remap drops both at once and is as cheap. Linux: `MADV_DONTNEED` as planned. `virtual.decommit` must not be used for the release (lazy on Linux).
- **D10: Linux holds (pagemap). macOS: neither of D10's sources works, and the replacement is a design question left to the owner** (see below). The initiative has a dated note saying so; the decision itself is not made.

**Open question for the owner (D10 / REQ-009 on macOS).** macOS has no per-range, per-process residency source, so `env_resident_check` can't count "the map's pages actually present in the process" there. Options:
1. `env_resident_check` returns `Unsupported` (or -1) on macOS, and the macOS success-criterion test uses the process's `task_info` `resident_size` above a baseline taken after `env_open` (the test process holds nothing else of size). Production is Linux, where the check is exact. **Recommended.**
2. On macOS `env_resident_check` returns the process-wide `resident_size`: always an overcount, by everything else the host holds, so of little use to an application, but the same call works in tests.
3. A destructive check: `resident_size` before minus after remapping the whole map. Exact for the map, but it empties it (it is `env_sweep(env, 0)` with a measurement around it), so it is only usable in tests.
The measurement's figures above are what any of them would build on.

**Other finding, not this task's:** `test_del_reader_keeps_snapshot` (KV-T-0018) fails deterministically with `-define:ODIN_TEST_RANDOM_SEED=778714601451138` on the committed code (`free_ready` 1, expected 0), independent of this task's files (which don't run without the define). The next `scripts/test.sh` run with other seeds passed all three configurations and the four target checks (132 tests, the same count as before: the platform tests aren't registered without the define). Not investigated here.

### 2026-09-24: D10 decided; done

The owner chose option 1. On macOS `env_resident_check` returns a new `Error` value, **`.Unsupported`** (not `Invalid_Argument`: the call is valid, the platform can't answer it), with 0 bytes; Linux uses `pagemap`; the macOS success-criterion test compares the process's `task_info` `resident_size` with a baseline taken after `env_open`. Amended in KV-I-0004 (D10 and REQ-009, dated notes, the old text standing) and in KV-T-0024's acceptance criteria, which adds `.Unsupported` and implements both. The `test_del_reader_keeps_snapshot` failure noted above is being handled separately.
