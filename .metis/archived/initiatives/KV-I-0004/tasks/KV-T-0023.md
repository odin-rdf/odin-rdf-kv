# Eviction, env_sweep and the hard watermark

## Parent Initiative

[[KV-I-0004]]

## Objective

Keep the resident estimate under `mapped_budget` by evicting chunks, driven by the application through `env_sweep`, with inline eviction as the backstop (KV-I-0004 D8, D9). The store starts no thread (Q3).

## Acceptance Criteria

*(Amended 2026-09-24 for the owner's decision: `env_sweep` is the sleep path, and the end of every transaction keeps the budget. The criteria as first written are kept below them.)*

- [x] **Platform eviction** in `kv/os_*.odin`, with the methods KV-T-0019 confirmed: Linux `MADV_DONTNEED`; macOS a `MAP_FIXED` remap of the same file range followed by `MADV_RANDOM`. Every address stays valid.
- [x] **Eviction order:** clear `resident` (and decrement the count) before evicting the range, so a racing reader can only cause an overestimate.
- [x] **Eviction at the end of every transaction:** `txn_abort` (which `txn_commit` ends through), once the reader is deregistered and the writer mutex released: above B, evict down to 7/8 B through the CLOCK code with `try_lock`; one atomic load otherwise. Nothing with `mapped_budget = 0`.
- [x] **`env_sweep(env, target := -1) -> (evicted: int)`:** CLOCK over the chunk table under `evict_mutex`, clearing `referenced` on chunks it passes and evicting those without it. Target 0 (the sleep path) drops everything. With the default target: nothing at or below the budget B (one atomic load), otherwise evict down to 7/8 B. An explicit target in bytes trims to it. Uses `try_lock`: a concurrent call returns 0 at once. Safe from any thread, with or without a transaction open. Without a budget, only an explicit target evicts. Doc comment: the sleep path, the default target no application needs, held slices stay valid.
- [x] **Inline eviction (D8, amended):** a `page_ptr` whose CAS takes the count past B + 2 chunks waits for `evict_mutex` and evicts down to 7/8 B (`LOW_WATERMARK_EIGHTHS`). No code holding `evict_mutex` reaches `page_ptr`.
- [x] Chunks past the end of the file are never marked resident and are skipped.
- [x] `Stats` gains `evictions` (chunks), `sweeps`, `txn_end_evictions` and `inline_evictions` (calls that evicted something, by path).
- Tests:
  - [x] **the primary budget test:** a store with a budget and no `env_sweep` stays within B + 2 chunks plus one per thread under readers and a writer (TSan, repeated) (`test_evict_budget_no_sweep`; which path evicts more depends on timing, see the status update);
  - [x] one long transaction reading past the budget: inline eviction keeps it within B + 2, and its end brings the estimate within B;
  - [x] transaction ends, read-only and write, committed and aborted, bring the estimate within B; with `mapped_budget = 0` nothing is evicted;
  - [x] readers hold slices across evictions (by `env_sweep` and inline) and compare the bytes afterwards;
  - [x] readers and a writer running during `env_sweep(env, 0)`, with inline evictions racing them, under TSan, repeated;
  - [x] while another thread holds `evict_mutex`, `env_sweep` and a transaction end return at once, and a read past the hard watermark waits;
  - [x] `env_sweep(env, 0)` leaves an estimate of 0 (and nothing present, on Linux), and the next reads fault back in and count again;
  - [x] the default target is a no-op within budget;
  - [x] write transactions and commits work across evictions (the writer's reads through the map included).
- [x] Deliberate-bug checks, each failing a test, recorded here: evict before clearing `resident`; skip the `referenced` check; forget to re-apply `MADV_RANDOM` after a macOS remap; check at commit only (a read-only workload goes over budget).
- [x] `scripts/test.sh` and `scripts/test-linux.sh` (arm64, amd64) pass.

## Implementation Notes

### Technical Approach
- `evict_mutex` guards the CLOCK hand only; readers never take it, only `env_sweep` and the inline path.
- Evict contiguous runs of chosen chunks with one call where possible.
- `env_sweep(env, 0)` is the sleep path for an idle store (KV-I-0004 D9); its doc comment says so, and says that held slices stay valid.

### Dependencies
KV-T-0022 (the chunk table) and KV-T-0019 (the methods).

### Risk Considerations
- A macOS remap racing a writer's `pwrite` to the same range: the page cache is shared and `pwrite` doesn't go through the mapping, so it should be safe; the TSan stress includes a writer.
- If macOS eviction doesn't lower the resident size (KV-T-0019), the macOS tests assert the estimate only, and the OS-level assertions run on Linux.

## Status Updates

### 2026-09-24: built and tested; one decision open (the hard watermark under concurrency)

**Not completed and not committed**: the primary budget test fails with the approved `try_lock` at the hard watermark (below). Everything else is done and passes.

**Usage correction and decision (from the owner, relayed during the task).** The application doesn't call `env_sweep` after every request: it calls `env_sweep(env, 0)` when the process has seen no request for hours, to put the store to sleep. So (1) **the end of every transaction evicts** above B down to 7/8 B, with `try_lock`, after the transaction has released the reader table and the writer mutex; (2) **inline eviction at B + 2 evicts down to 7/8 B**, not back to B, 7/8 being the named constant `LOW_WATERMARK_EIGHTHS`; (3) `env_sweep` stays, target 0 being the sleep path and the default target something no application needs; (4) `Stats` counts the paths separately; (5) the primary test is a store with a budget and no `env_sweep` at all. D8, D9 and Q3 are amended in KV-I-0004 with dated notes, the old text standing, and the acceptance criteria above are amended the same way.

**What was built.**
- `kv/os_darwin.odin`, `kv/os_linux.odin`: `os_evict(fd, addr, offset, size)`. macOS: `mmap(MAP_SHARED | MAP_FIXED)` of the same file range over itself, then `posix_madvise(RANDOM)` on it again. Linux: `madvise(MADV_DONTNEED)` through the local binding (glibc's `posix_madvise` ignores it).
- `kv/chunks.odin`:
  - `Chunk_Table` gains the watermarks in chunks (`limit` B, `low` 7/8 B, `high` B + 2; `limit` and `high` are `max(int)` without a budget, so every check is one load and compare), `end` (one past the highest chunk ever made resident, raised in the slow path; eviction looks at nothing from there on, which is how chunks past the end of the file are skipped), the counters `evictions`, `sweeps`, `txn_end_evictions`, `inline_evictions`, `evict_mutex` and the CLOCK `hand`.
  - `chunks_evict(env, target)`: CLOCK, under `evict_mutex`. A chunk with `referenced` has it cleared and survives; one without is cleared by a CAS from the value just read to 0 (which fails, sparing the chunk, if a reader marked it meanwhile), uncounted, and only then evicted. Consecutive chosen chunks are evicted with one call. At most two turns of the hand, so readers that keep everything referenced can't hold it forever.
  - `chunks_evict_all(env)`: target 0. Clears every flag below `end` (CAS), then evicts the whole range `[0, end)` with **one call, counted or not**. That also drops pages faulted in through slices held across an earlier eviction (Q4), which CLOCK never sees because they aren't flagged; without it, a sleeping store kept them (seen on Linux: 74 chunks present and uncounted after the concurrent test's last sweep, 0 with it).
  - `chunk_resident_added(env, i, resident)`: raises `end`, and above `high` evicts inline (`try_lock`) down to `low`.
  - `chunks_txn_end(env)` (`#force_inline`: one load and compare), called at the end of `txn_abort` after the reader is deregistered and the writer mutex released, before `active_txns` is decremented; above `limit` it evicts down to `low` (`try_lock`).
  - `env_sweep(env, target := -1)`: default target as the end of a transaction; `target ≥ 0` in bytes (rounded down to chunks), 0 through `chunks_evict_all`; `try_lock`, returns 0 at once if eviction is under way. Doc comment: the sleep path, the default target no application needs, held slices stay valid.
  - A failed OS call (never seen) puts the chunks back as resident (`chunks_restore`), keeping `faults − evictions = resident`.
- `kv/env.odin`: `Stats` gains `evictions`, `sweeps`, `txn_end_evictions`, `inline_evictions` (live). **`os_map_reserve` takes an alignment and `env_open` passes the chunk size** (next item).
- **The map is reserved at a chunk-aligned address** (`kv/os_posix.odin`): an anonymous `PROT_NONE` reservation of `map_size + align`, the file mapped `MAP_FIXED` at the aligned address inside it, the slack unmapped. Found by the Linux OS check: Linux's fault-around window (64 KiB, KV-T-0019) is aligned **by virtual address**, and `mmap` only aligns to the OS page, so with the map 60 KiB off a 64 KiB boundary a read of one chunk mapped pages of its neighbour, which the estimate never counted (a present-but-uncounted chunk in 1 of 6 runs of `test_sweep_estimate_not_under`; 0 of 45 runs since). KV-T-0019's "aligned, so it stays inside one chunk" assumed an alignment nothing guaranteed. `test_chunk_options` and `test_pwrite_visible_through_map` check the alignment.

**Tests** (`tests/evict_test.odin`, 12 + a bench; 160 tests in all, from 149): `test_sweep_default_target` (watermarks, no-op within budget with no flag touched, 7/8 B above it, a sweep evicting nothing isn't counted), `test_sweep_to_zero` (no budget: only an explicit target evicts; Q4 in practice: the OS check is only asserted where no held slice is read after an eviction. Where one is (the concurrent test, the write test), the uncounted chunks are logged: 74 with 4 counted after the concurrent test before its final sleep (a 4-chunk budget, 32 values held per request), 2–5 after the write test.

**The open question: B + 2 under concurrency.** `test_evict_budget_no_sweep` (4 readers, 2 000 requests each of 2 gets, nine in ten from a quarter of the keys, over a 60-chunk database with B = 24; a writer committing 4 puts at a time; no `env_sweep`) asserts that the estimate each thread sees after its transactions stays within B + 2 + one chunk per thread, and fails with `try_lock` at the hard watermark:

| hard watermark | macOS (-o:speed, 5 runs) | Linux arm64 (-o:speed, 5 runs) | macOS, full suite in parallel |
|---|---|---|---|
| `try_lock` (approved) | 51, 54, 69, 76, 91 | 53, 54, 56, 60, 60 | 95 (every chunk) |
| waiting `mutex_lock` | 28, 29, 29, 29, 29 | 28, 28, 28, 29, 29 | — |

Why: an eviction holds `evict_mutex` for 17–67 µs on average (up to ~1 ms on macOS, where the remap contends with the readers' faults for the VM map), and while it does, every other thread that passes B + 2 goes on reading and faulting chunks in. CLOCK can't catch up: newly faulted chunks arrive referenced, so the hand must pass them twice. With `try_lock` the bound is therefore "B + 2 plus whatever the other threads fault during one eviction", not B + 2. Waiting at the hard watermark (only there: the transaction end and `env_sweep` keep `try_lock`) is back-pressure on exactly the threads over the limit, and holds B + 2 + one chunk per thread. Its costs: a reader past the hard watermark waits for the eviction under way (an eviction call took 14–18 µs on average on macOS and 8–11 µs on Linux in those runs, at most 0.25 ms on macOS); and **a thread holding `evict_mutex` must never reach `page_ptr`**, or it deadlocks on itself. Nothing in `kv/` does (eviction reads no page), but `test_sweep_try_lock` does on purpose, holding the mutex to simulate another evictor: the full suite with the waiting lock hung there, so under (a) that test takes the lock from a second thread. The waiting lock was only measured with the primary test, as in the table.

Options for the owner: (a) wait at the hard watermark (`mutex_lock`), keeping `try_lock` for transaction ends and `env_sweep` (**recommended**: it is the only one that makes B + 2 a bound under concurrency, and the wait falls only on threads already over it); (b) keep `try_lock` and state the bound as B + 2 plus the faults of other threads during one eviction (the test would then only log it); (c) something in between, such as waiting only beyond a second, higher mark. The code as it stands is (b)'s, i.e. the approved design; switching to (a) is one line in `chunk_resident_added` plus moving `test_sweep_try_lock`'s lock to another thread.

**Deliberate-bug checks** (each restored; the file compared with its saved copy):
- **Evict before clearing `resident`**, three variants, against `test_sweep_estimate_not_under` on Linux (the only platform with a per-range oracle): the sleep path evicting the range and then clearing every flag failed **8 of 8** runs; CLOCK evicting a chunk and then clearing it unconditionally (atomic exchange to 0) failed 2 of 8 (a lost mark only shows if nothing reads its chunk again before the round ends); CLOCK evicting and then clearing with the CAS as in the real code failed 0 of 25. The last is expected: that CAS fails whenever a reader marked the chunk after the hand read it, so the chunk stays counted, and the order only matters when the clear can wipe a reader's mark. The real code clears first and uses the CAS on both paths. On macOS no test can see the order (no per-range source, KV-T-0019).
- **Skip the `referenced` check** (evict everything the hand passes): `test_sweep_spares_referenced` fails ("resident chunks [10], expected [6]"; also no referenced flag left after the first sweep).
- **Forget `MADV_RANDOM` after the macOS remap:** `test_sweep_to_zero` fails ("the map lost MADV_RANDOM"), through `advice_random` reading the region's behavior with `mach_vm_region`.
- **Check only when a write transaction ends** (the new path): `test_evict_at_txn_end` fails ("read transaction 3: 9 chunks resident after it ended") and so does `test_evict_long_txn_inline` (8 chunks after each transaction, budget 6).

**Measurements** (`test_bench_sweep`, `-o:speed`, 256 KiB chunks, 24 chunks faulted in by touching every page; reported, not asserted; KV-T-0024 measures properly): `env_sweep` with nothing to do **1.2–2.6 ns** (macOS); `env_sweep(env, 0)` over 24 chunks **14–15 µs** per call on macOS (0.6 µs per chunk, one remap), 49 µs on Linux arm64 (2.0 µs per chunk, one `madvise`); evicting half of them by CLOCK 6–7 µs (macOS), 27 µs (Linux). ### 2026-09-24: the owner chose (a); done

**Decision:** at the hard watermark a thread **waits** for `evict_mutex` (`mutex_lock`) and then evicts whatever is still above 7/8 B; transaction ends and `env_sweep` keep `try_lock`. D8 amended in KV-I-0004 with the rule and the measured bound. The invariant it needs is stated in `Chunk_Table`'s doc comment, on `chunk_resident_added` and in `CLAUDE.md`: **no code holding `evict_mutex` may reach `page_ptr`** (or `chunk_touch`, `chunks_touch_range`), or it waits on itself; nothing in `kv/` does, since eviction reads no page.

**Changed:** `chunk_resident_added` takes the lock with `mutex_lock`. `test_sweep_try_lock` now holds the lock from a second thread (`Lock_Holder`): with it held, reading up to B + 2, `env_sweep(env, 0)`, `env_sweep(env)` and a transaction end evict nothing; a read past B + 2 then waits until the holder releases (checked by time: the read returns after the release) and evicts to 7/8 B. `test_evict_budget_no_sweep` no longer asserts that transaction ends do most of the evicting, only that they evict: the watermark is global, so several short transactions together pass it and evict inline, and which path does more depends on timing (inline calls were 55–57% of the eviction calls in `-o:speed` on macOS, 10–30% elsewhere). `test_evict_at_txn_end` is what checks that short transactions alone never evict inline.

**The primary test, repeated** (`test_evict_budget_no_sweep`: B = 24, 4 readers of 2 000 requests, a writer, no `env_sweep`; the highest estimate any thread saw after one of its transactions; the bound asserted is B + 2 + 5 = 31):

| platform | build | runs | highest estimate |
|---|---|---|---|
| macOS | debug | 5 | 28 each |
| macOS | `-o:speed` | 5 | 28, 29, 28, 29, 28 |
| macOS | `-sanitize:thread` | 4 | 29 each |
| Linux arm64 | debug | 5 | 28, 28, 28, 28, 29 |

| Linux amd64 | debug | 5 | 28, 29, 28, 28, 28 |
| Linux amd64 | `-o:speed` | 5 | 28, 29, 28, 29, 28 |

So the bound is B + 2 plus about one chunk per thread, as expected, against 51–96 chunks with `try_lock`.

**Deviations from the task as written** (both kept by the owner):
- **The map is reserved at a chunk-aligned address** (`os_map_reserve(fd, map_size, align)`), because Linux's fault-around window is aligned by address and otherwise crossed into a neighbouring, uncounted chunk (first status update).
- **`env_sweep(env, 0)` evicts the whole range below `end` with one call**, counted or not (`chunks_evict_all`), rather than by CLOCK, so the sleep path also drops pages faulted in through held slices (Q4).
Also beyond the first criteria, from the owner's decisions: eviction at every transaction end, `txn_end_evictions`, inline eviction to 7/8 B, and waiting at the hard watermark.
