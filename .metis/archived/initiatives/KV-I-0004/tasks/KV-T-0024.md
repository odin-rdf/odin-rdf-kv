# OS residency check and the memory-budget criterion

## Parent Initiative

[[KV-I-0004]]

## Objective

Check the estimate against the OS (KV-I-0004 D10) and show the vision's success criterion: with a database of about 100 MB and a 20 MB budget, the resident footprint stays within about 1–2 chunks of the budget under mixed load, on macOS and Linux. Then close the initiative: measurements, vision, `CLAUDE.md` and Results.

## Acceptance Criteria

- [x] **`env_resident_check(env) -> (resident_bytes: int, err: Error)`:** counts the map's pages present in the process over the file's extent. Linux: `/proc/self/pagemap` present bits, never `mincore` (it reports the page cache). **macOS: returns `(0, .Unsupported)`**, a new `Error` value added by this task (KV-T-0019 found no macOS source that counts a range's pages mapped into the process: `mincore` and `mach_vm_region` both report the page cache; D10 as amended 2026-09-24). It doesn't change the estimate (Q4).
- [x] Tests (Linux): after reads, the check is at most the estimate plus a small tolerance; after `env_sweep(env, 0)`, it is near 0. On macOS, a test that the check returns `.Unsupported`, and the same two checks made against the process's `task_info` `resident_size` above a baseline taken after `env_open` (after `env_sweep(env, 0)` it is back near the baseline).
- [x] **The criterion test**, on demand (a define, like the steady tests): a database of about 100 MB; `mapped_budget` about 15 MB and the default 4 MiB dirty pool; reader, scanner and writer threads, with **no `env_sweep` calls**: the budget is held by the check at the end of every transaction and by inline eviction (KV-I-0004 D8/D9 as amended 2026-09-24). Report how many evictions each path made. Sample the resident figure plus `dirty_committed` throughout and assert they stay within 2 chunks of the total budget. **Linux:** the resident figure is `env_resident_check`. **macOS:** it is the process's `task_info` `resident_size` above a baseline taken right after `env_open` (the test process holds nothing else of size; allow for the test's own allocations in the tolerance, and record it). Run on macOS and Linux (arm64, amd64); KV-T-0019 showed macOS eviction (the `MAP_FIXED` remap) is effective, so both assert.
- [x] The drift between the estimate and the OS figure (`pagemap` on Linux, `resident_size` above the baseline on macOS) is reported (Q4 decides nothing is corrected unless it's large).
- [x] **Measurements, recorded in this task and the initiative's Results:** the time the end-of-transaction check adds (under budget; when it evicts) and the time `env_sweep(env, 0)` takes to put a store to sleep; the memory left after `env_sweep(env, 0)` against after `env_close`; the time `env_open` takes to wake a store, with a short and a long free list.
- [x] **Capacity-planning figures** for the first deployment (the user's hardware sheet), measured from the OS, per store, in the same form as the design bound `mapped_budget + 2 × chunk_size + dirty_budget + fixed`. A table on Linux (the production platform) and macOS, for at least two settings (the default 256 KiB chunks with a 15 MB budget, and 64 KiB chunks with an 8 MiB budget):
  - **active, worst case:** the peak resident figure plus the peak dirty pool under the criterion test's mixed load, against the design bound;
  - **active, typical:** resident and dirty figures under a light request-like load (single-entry reads and writes of conversation-sized values, a few per second), after it settles;
  - **asleep:** after `env_sweep(env, 0)`, what the store still holds: the resident figure, `free_list_bytes`, the chunk table and the fixed structures, against the same after `env_close`;
  - **fixed structures** broken down: chunk table, reader table, `Env`, free list, pool bookkeeping;
  - reserved address space (`map_size` + `dirty_budget`) stated separately as virtual, not RAM.
  The table goes in this task's Status Update and in KV-I-0004's Results, with the method used for each figure.
- [x] The full matrix passes on macOS and Linux. The steady-state tests run once each, debug only, with `-define:KV_STEADY_COMMITS=1000` (the user avoids the full-length runs for their CPU use); record that the full `scripts/test.sh --steady` was skipped.
- [x] Documentation:
  - the vision's Current State, and its memory-budget section amended: no sweeper thread; the store checks its budget at the end of every transaction and evicts inline as a backstop; the application calls `env_sweep(env, 0)` to put an idle store to sleep (a dated note, the old text standing);
  - step 7's scope gains "killed after a spill, before commit";
  - `CLAUDE.md`: the new options, `env_sweep`, the test defines, and the code map;
  - KV-I-0004's Results: the exit-criteria table, deviations and known limitations, as KV-I-0003 has.

## Implementation Notes

### Technical Approach
- Read `/proc/self/pagemap` in batches over the file's pages only (8 bytes a page: 200 KiB for a 100 MB file).
- The 100 MB database is built once per run in a temporary directory with the bulk of values in the few-hundred-byte range and some overflow values, like conversation messages.

### Dependencies
KV-T-0021, KV-T-0022 and KV-T-0023. Last task of KV-I-0004.

### Risk Considerations
- The criterion test is timing-dependent; it asserts on samples of the resident figure, not on throughput, so a slow CI machine only makes it slower.

## Status Updates

### 2026-09-24: done

**What was built.**
- `Error.Unsupported` (`kv/types.odin`): the call is valid but the platform can't answer it.
- `env_resident_check(env) -> (resident_bytes: int, err: Error)` (`kv/chunks.odin`), with `os_resident` in the platform files. It counts the map's pages present in the process over the file's extent (`Stats.file_pages`, read under `snapshot_mutex`, rounded up to the OS page, at most `map_size`). **Linux** reads `/proc/self/pagemap` in batches of 1,024 entries into a buffer on the stack (8 KiB, nothing allocated) and counts bit 63; it never uses `mincore`. **macOS** returns `(0, .Unsupported)`. It is safe from any thread and doesn't change the estimate (Q4). The doc comment says how the two figures differ in both directions: whole chunks against pages, and held slices.
- `tests/resident_test.odin`, `test_resident_check` (in the ordinary suite, so 161 tests). **Linux:** after open, the check is within the estimate; after a full scan it is at least the tree and within the estimate; after `env_sweep(env, 0)` it is exactly 0. Then the database is reopened with a budget of 32 chunks for 400 single-get requests, and after every request whose transaction evicted only at its end, the check is within the estimate plus one chunk; finally `env_sweep(env, 0)` gives 0 again. **macOS:** the check returns `(0, .Unsupported)`. The process's file-backed resident size (`task_info` `external`), above a baseline taken after `env_open`, grows by at most the estimate plus 1 MiB during a full scan (and by at least half the tree, so that the check sees the map at all), and is back within 1 MiB of the baseline after `env_sweep(env, 0)`; the whole `resident_size` is logged beside it. The other tests run on other threads of the same process and map their own databases, so a disturbed attempt is repeated, up to 5 times. In every run so far the first attempt passed: +20,692,992 bytes against an estimate of 20,709,376 (`resident_size` the same), and −16,384 after the sleep. The task named `resident_size`; `external` is used because under `-sanitize:thread` `resident_size` grows by three times the file (the sanitizer's shadow of every byte read: +62 MB for a 20.7 MB scan), and because of malloc's retained pages (Deviations).
- `tests/criterion_test.odin`, `test_memory_criterion`, registered only with `-define:KV_CRITERION=true` (plus `KV_CRITERION_SECONDS`, default 10, and `KV_CRITERION_PAUSE_US`, default 200). It builds the database once per run in a temporary directory: 1,400 conversations of 40 messages (key `c%05d/%05d`, one entry per message; nine values in ten are 100–899 bytes and one in ten is an overflow value of 2–16 KiB), 105.4 MB of tree, a 107.1 MB file, built in 0.2–0.6 s. For each setting (256 KiB chunks with a 15 MiB budget, then 64 KiB chunks with 8 MiB, both with the default 4 MiB dirty pool) it runs:
  1. **the criterion:** two readers (three messages of a random conversation), a scanner (a whole conversation; one request in 50 reads 4,000 messages in a row) and a writer (one to three messages appended to a conversation; one request in 100 appends 1,500 messages, more than the pool holds), for 10 s, with **no `env_sweep` call**. A sampler thread samples the figure throughout and asserts it stays within `mapped_budget + dirty_budget + 2 × chunk_size`. Every value read is checked against its key. It also asserts that both eviction paths were used, that there was no sweep, and that the writer spilled;
  2. **typical:** 2,000 single-entry requests from sleep, four reads to one write, with the figures after each of the last 1,000;
  3. **the end-of-transaction check's cost;**
  4. **sleep:** `env_sweep(env, 0)` from the budget, five times, and the store's figures asleep, against `env_close`.

  Before the settings it runs a short warm-up pass that isn't reported, and it ends with **wake**: `env_open` with the free list as built, then again after deleting every other conversation with a reader held. Values go through stack buffers and a per-thread heap buffer, not the temporary allocator.
- `process_file_resident` in `tests/platform_darwin_test.odin` (`task_info`'s `external`) and `tests/platform_linux_test.odin` (`RssFile` in `/proc/self/status`), so the test compiles on both.

With 256 KiB chunks a touch maps 64 KiB of the chunk, and the margin is large.

**Drift between the estimate and the OS (Q4).** On the samples, the OS's mapped figure averaged a fraction of the estimate (estimate = `resident_chunks × chunk_size`), because the estimate counts whole chunks and the OS counts pages. Linux 256 KiB: 30–37%. Linux 64 KiB: 82–101% (fault-around, above). macOS (16 KiB pages): 14–21% at 256 KiB and 35% at 64 KiB. **In no consistent sample was the OS above the estimate** ("at most 0.00 MiB above"). At the end of each Linux run, 0 chunks were present and uncounted, and at most 1 was counted and not present. The readers compare the values they read, which after an eviction faults pages back in uncounted, but a later read marks those chunks again soon. **So Q4 stands: no correction.** One source of undercount was found and is not corrected: inline eviction inside an operation. With a small budget (B = 8 and four gets per transaction), CLOCK's second turn, finding every chunk referenced, can evict the chunk the current `get` has just marked, and the operation then reads its page back in uncounted. That showed up as 2–3 uncounted chunks after some requests, which is why the Linux budget test checks strictly only after transactions without an inline eviction (it logs the others).

**Sleep against close.** Asleep, the store holds **no mapped pages** (Linux: `pagemap` 0 over the file; macOS: the file-backed resident size back at or below its baseline, which included the meta pages) and **no dirty memory**. What it keeps is the heap below, 40–68 KiB after these runs, plus the address-space reservations. After `env_close` it holds nothing. Waking from sleep costs nothing up front: each chunk read after it faults in from the page cache for about 5 µs (KV-T-0019). Waking from close costs `env_open` first (above) and then the same faults. The process's own resident size after close was 0–8 MiB above what it was before `env_open`. That is not the store: it is what malloc kept resident after frees during the test, the same after `env_close` as asleep.

Reading it for the hardware sheet:
- **A store in use sits at its budget in the estimate.** The end of every transaction brings it back to at most B, so after a few hundred random reads `resident_chunks` is 56–60 of 60, or 120–128 of 128. What the OS actually holds is lower whenever reads touch only part of each chunk: with 256 KiB chunks, about 4.25 MiB on Linux and 1.1 MiB on macOS for single-entry requests. With 64 KiB chunks on Linux, fault-around makes it the whole budget.
- **For RAM per server, plan with the design bound for stores in use, and with the fixed structures for stores asleep.** A store's dirty memory is 0 between requests, and a few KiB up to the full 4 MiB pool only during a write transaction. For example, 250 stores at 256 KiB / 15 MiB: at most about 19.5 MiB each while in use (4.3 MiB typical on Linux), and about 42 KiB each asleep, plus 16 B per free-list record.
- **The free list is the one fixed structure that grows:** 16 B per record, with up to about 0.75 MiB and a 5 ms wake after deleting 45,000 pages' worth with a reader held.
- Linux figures are from OrbStack's VM (not bare metal); per-process page tables and `pagemap` behave the same in a container, and cgroup accounting was not measured.

**Decisions and deviations.**
- **On macOS the criterion asserts the file-backed resident size (`task_info` `external`) above a baseline, plus `dirty_committed`, not the whole `resident_size`.** `resident_size` also carries whatever macOS malloc keeps resident after a free: the test's threads, the test runner's 4 MiB temporary-allocator block as its bump pointer first walks through it, and regions of freed allocations (`MALLOC_SMALL (empty)`, `MALLOC_LARGE (empty)` in `vmmap`, 4–8 MiB in a pass, staying after `env_close`). Checked: `external` follows the map exactly (+20,692,992 bytes after a full scan, the same as `resident_size`, and −16 KiB after the sleep). `resident_size` is still sampled and logged, and it stayed within the limit too (above). The test also warms and resets the temporary allocator before its baselines, and runs a warm-up pass that isn't reported.
- **On Linux only consistent samples count.** A `pagemap` walk over 100 MB takes 0.1–0.3 ms and is not atomic. At full speed, up to about 3,000 chunks were faulted in during one walk (the sampler descheduled among five busy threads), so a walk counted chunks that were never resident together: 2.75–4.6 MiB "above the estimate", and a spurious failure at 64 KiB. A sample now counts only if `chunk_faults` and `evictions` didn't change during its walk: then residency didn't change while the walk ran, and the walk read one instant. About half the samples are dropped (the log gives the counts; 1,500–3,200 consistent per setting and run).
- **The readers and the scanner pause 200 µs between requests** (`KV_CRITERION_PAUSE_US`). Without the pause they made about 35,000 requests a second each, and almost no walk was consistent. With it, the load is still 600–4,300 requests a second per thread on a working set seven times the budget, which is still far above the deployment's rate.
- **The typical load runs without pauses:** the store does nothing on a timer, so only the sequence of requests matters, not "a few per second".
- **The criterion test is also the capacity measurement**, so that the 100 MB database is built once per run.
- **The Linux budget test uses B = 32 and one get per request,** and checks strictly only after transactions that didn't evict inline (see the drift paragraph). With B = 8 and four gets, three requests in four evicted inline.
- Found and fixed in the test while building it: `path` was allocated in the temporary allocator, which a later `free_all` released (`env_open` got ENOENT); and the scanner's check for the end of a conversation was off after its first entry, so every scan read about 30,000 entries.

**Deliberate-bug checks** (each restored and compared with the saved file):
- **`env_resident_check` counts the page cache** (Linux `os_resident` using `mincore`): `test_resident_check` fails ("after open: the OS holds 20697088 bytes of the map, the estimate is 65536"; "after env_sweep(env, 0): the OS holds 20697088 bytes").
- **It reads the wrong range** (the `pagemap` offset without the × 8): `test_resident_check` fails ("after a full scan the OS holds 0 bytes of the map, the tree is 20688896").
- **macOS returns `.None` instead of `.Unsupported`:** `test_resident_check` fails ("expected err to be Unsupported, got None").
- **No eviction at transaction ends or inline** (`limit` and `high` left at `max(int)` with a budget set): `test_memory_criterion` fails: 8,597 of 8,788 samples over, peak 111.55 MiB against a 19.50 MiB limit, estimate 447 chunks, and "an eviction path unused".
