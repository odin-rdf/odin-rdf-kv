# Seeded fuzz mode over the model

## Parent Initiative

[[KV-I-0005]]

## Objective

The correctness half of step 7: long, seed-reproducible runs of the existing model, on demand and cheap in CPU and CI minutes (KV-I-0005 D4, D5).

## Acceptance Criteria

- [x] `-define:KV_FUZZ=true` registers `test_fuzz_model`: `run_model` for `KV_FUZZ_OPS` operations (default 10⁶) over `KV_FUZZ_SEEDS` consecutive seeds (default 1) from the runner's seed, alternating the default pool and `MIN_DIRTY_BUDGET`, and varying the key count per seed.
- [x] `KV_FUZZ_CHECK_EVERY=k` (default 1) reaches `run_model`: the full `model_compare` and `space_check` run every *k* commits and before every reopen and on the last commit. The ordinary model tests keep `k = 1`.
- [x] The test logs whether `kv.NO_SYNC` is set and recommends it; the doc comment and `CLAUDE.md`'s build section give the command, with `ODIN_TEST_THREADS`.
- [x] Each failure message carries the seed and the operation, as the model already does; a failing seed from a multi-seed run reproduces alone.
- [x] Measured and recorded: operations per second with and without `KV_NO_SYNC`, and with `k = 1` and `k = 10`, on macOS arm64.
- [x] Deliberate-bug check recorded: a bug the ordinary model test at its seed does not hit but the fuzz run does (or, if none is found, a bug both hit, and a note that the fuzz run found it within N operations).
- [x] `scripts/test.sh` passes.

## Implementation Notes

### Dependencies
KV-T-0026 (`KV_NO_SYNC`).

## Status Updates

### 2026-09-25 — implemented and verified

**What was built.**
- `tests/fuzz_test.odin`: `test_fuzz_model`, registered only under `-define:KV_FUZZ=true` (the procedure compiles in every build, the `KV_STEADY` idiom). `KV_FUZZ_OPS` (default 10⁶), `KV_FUZZ_SEEDS` (default 1), `KV_FUZZ_CHECK_EVERY` (default 1). Each seed gets a new database in its own temporary directory, `rand.reset(seed)` just before `run_model` (the state a run with `ODIN_TEST_RANDOM_SEED` set to it starts from), and a log line with its pool, key count, ops/second and `Model_Stats`; the run ends with a total. It logs whether `kv.NO_SYNC` is set, and warns and recommends it when it isn't. The doc comment has the command line and how to reproduce a seed.
- `run_model` (`tests/model_test.odin`) gained `check_every := 1` and `run_seed: Maybe(u64) = nil` (the seed messages show; `t.seed` by default). Two `Model_Stats` fields: `full_checks` and `max_depth` (the deepest tree a commit left, for judging what a fuzz seed covered).
- Failure messages now carry the operation everywhere: `model_compare` has an optional `op` (printed when ≥ 0; the two isolation-test callers are unchanged), and `verify_committed`, `held_release` and `map_full_reopen` pass it, so `after commit/abort`, `after reopen`, `held reader on release` and their `space_check` messages read `[seed N] op M: …`. Before, only the in-transaction checks had the operation.
- `CLAUDE.md`'s build section: the fuzz command line, the defines, and how to reproduce a seed.

**Decisions.**
- **A seed's options come from the seed alone:** odd seeds open with `MIN_DIRTY_BUDGET`, even ones with the default pool (so consecutive seeds alternate, as the criterion asks), and the key count is one of 100, 500, 1,000, 3,000, 10,000, picked by a multiplicative hash of the seed. Deriving them from the seed's index in the run would have made seed N of a multi-seed run a different test from seed N alone. Reproducing needs only `-define:ODIN_TEST_RANDOM_SEED=N -define:KV_FUZZ_SEEDS=1` and the same `KV_FUZZ_OPS` (the last operation always commits, so the op count is part of the run); the test prints exactly that line on failure.
- **k counts transaction ends (commits and aborts), not commits only.** With k = 1 that is exactly the old behaviour (the check after every commit and every abort); counting commits only would have needed a special case to keep checking after aborts at k = 1. A check is also forced before a reopen (the reopen decision moved above the check for that), and at the last operation. The check after a reopen and a held reader's check on release always run: `held_release` checks the reader's own snapshot against its own model copy and needs nothing from the last-commit check, and both happen rarely (a reopen per 10⁴ operations, a reader released every few hundred).
- **The pre-commit `space_check` on the write transaction follows k,** running on the same transactions as the check after them. It costs about as much as the reader's `space_check`, and a page lost or doubled in the write transaction is still lost or doubled in the commit the following check reads (after an abort it was never written). Leaving it at every transaction would have kept most of k's cost.
- **The checks draw no random numbers,** so a seed runs the same operations at any k: a failure found at k = 10 is rerun at k = 1 to be reported at its transaction. Checked below (seed 7 fails at the same operation at k = 10 and k = 1).

**Measured** (macOS arm64, `-o:speed`, `-define:ODIN_TEST_THREADS=1`, one seed each):

| Seed | Pool, keys | Syncs | Ops | k = 1 | k = 10 |
|---|---|---|---|---|---|
| 100 | default, 3,000 | `KV_NO_SYNC` | 10⁶ | 8.2 s, 122,600 ops/s | 3.3 s, 306,600 ops/s |
| 105 | smallest, 3,000 | `KV_NO_SYNC` | 10⁶ | 8.5 s, 117,700 ops/s | 3.3 s, 299,100 ops/s |
| 113 | smallest, 10,000 | `KV_NO_SYNC` | 10⁶ | 16.1 s, 62,200 ops/s | 6.0 s, 165,800 ops/s |
| 100 | default, 3,000 | `KV_NO_SYNC` | 10⁵ | 0.9 s, 108,500 ops/s | — |
| 100 | default, 3,000 | real | 10⁵ | 3.5 s, 28,400 ops/s | 3.0 s, 33,200 ops/s |

The real-sync run was kept to 10⁵ operations to spare the SSD: 339 commits cost 2.6 s of syncs, about 7.7 ms a commit (two `F_FULLFSYNC`s). **Extrapolated, not measured:** 10⁶ operations with real syncs (3,362 commits) would be about 34 s at k = 1 and 29 s at k = 10 — 4× and 9× the `KV_NO_SYNC` figures, which is why the test recommends it. The 10⁶ `KV_NO_SYNC` figure at 3,000 keys (8.2 s) is below the design's estimate of 13 s; the key count matters more than anything else (10,000 keys doubles it), and the smallest pool costs almost nothing extra. k = 10 is 2.5–2.7× faster: at k = 1 the full checks, not the operations, are most of the time. With 100 keys the smallest pool never spills (the tree fits in 49 pages), so those seeds exercise small trees and frequent root collapse rather than spilling. Trees reach depth 4 at 3,000 keys as well as at 10,000 (the long keys), so depth is not what the larger key counts add; what they add is scan and check cost per operation, and more pages per commit.

**Deliberate-bug check** (every run `-o:speed`, `KV_NO_SYNC`, under `timeout -s KILL 300`; the bug reverted from a saved copy and `git diff kv/` empty afterwards). The bug is an off-by-one at an overflow size boundary: in `overflow_write`, `len(tail) > 0` became `len(tail) > 1`, so a value whose bytes after the first page leave exactly one byte on the run's last page loses that byte (the reader sees whatever the page held). About one overflow put in 4,096 hits it.
- **The ordinary tests at a fixed seed miss it:** `test_model_randomized` and `test_model_randomized_min_pool` (10⁵ operations each) **passed** at seeds 4, 5 and 6, and failed at 1, 2 and 3.
- **The fuzz run catches it at every seed the ordinary tests missed:** seed 4 (default pool, 100 keys) at op 298,166; seed 5 (smallest pool, 10,000 keys) at op 662,488; seed 6 (default pool, 3,000 keys) at op 897,636 — all `after commit/abort: get returned a wrong value`, all within the default 10⁶ operations. So the fuzz run found it within about 3×10⁵–9×10⁵ operations on seeds where 10⁵ was not enough.
- **Multi-seed reproduction:** `KV_FUZZ_OPS=300000 KV_FUZZ_SEEDS=6 KV_FUZZ_CHECK_EVERY=10` from seed 5 passed seeds 5 and 6 and failed at `[seed 7] op 251718: get of id 272`, printing the reproduction line. Run alone (`ODIN_TEST_RANDOM_SEED=7 KV_FUZZ_SEEDS=1 KV_FUZZ_OPS=300000`) it failed at the same operation, at k = 10 and at k = 1.

Not checked with a deliberate bug: the k-thinning itself. What shows it is sound is the reproduction above (it changes no operation), the `full_checks` counts (at 10⁶ operations of seed 100, 3,959 at k = 1 for 3,362 commits and 597 aborts, and 438 at k = 10: a tenth, plus those forced before the 98 reopens), and k = 1 being the ordinary tests' path, which the full suite runs.

**Deviations.** Beyond the criteria: the operation number in the last-commit, reopen and held-reader failure messages (the criterion says "as the model already does", but those three phases had only the seed), and `Model_Stats.max_depth`/`full_checks`. k counts transactions, not commits (above).

**Verification.** `scripts/test.sh -define:ODIN_TEST_THREADS=4`: all configurations pass — debug 164, `-o:speed` 164, ASan 164, hooked/no-sync 183 tests — and every cross-target check. The fuzz test is not registered there (it needs `KV_FUZZ`); `odin check tests -vet -strict-style -define:KV_FUZZ=true` passes. The ordinary model tests run at k = 1 unchanged. `kv/` is untouched, so the Linux container was not run. (One re-run of seed 100 at k = 1 while the suite ran in parallel took 12.1 s against 8.2 s alone; the table's figures are from runs with nothing else going.)
