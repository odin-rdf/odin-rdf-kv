# A power loss during creation can leave a file that never opens

## Objective

Found by KV-T-0029's creation sweep (2026-09-25); **a decision for the owner**. `init_meta_pages` truncates the new file to two pages, writes both meta pages, then syncs once. Under the power-loss model two kinds of image stay `.Corrupted` under D6 as decided, so the application fails to start until someone deletes the file:

- **Sizing lost, a meta write kept:** the file is shorter than the page a meta page describes (96 bytes, `page_size + 96`, or a torn prefix), so no meta page can be valid.
- **Sizing kept, neither meta write whole, at least one torn:** not all zero, so D6 doesn't apply.

Such a file holds no data: creation never finished, so nothing was ever committed.

## Options (from KV-T-0029's status update)

1. **A sync after the truncate** in `init_meta_pages`. It removes the "sizing lost" class, at the cost of one extra sync at creation only. **Recommended now.**
2. The torn class comes only from a tear inside the 96-byte meta write, which sits within one 512-byte sector. If sector writes are treated as atomic (LMDB's assumption), option 1 alone makes every creation image open. If they are not, the choices are:
   - widen D6 to "at most two pages, nonzero bytes only inside the two meta prefixes", which is a guess based on damaged bytes;
   - or create at a temporary path and rename it into place (needs a directory fsync, and the journal doesn't model it).

## Acceptance Criteria

- [x] The owner decides option 1, and decides the sector-atomicity question separately. *(Option 1 taken 2026-09-25. The sector-atomicity question is not decided: it is split into **KV-T-0038**, an open owner decision.)*
- [x] If option 1 is taken: the sync added; `crash_sweep_create_power`'s shape assertion (which requires both refused kinds to occur) updated; the power-loss creation sweep shows which images remain refused.

## Status Updates

**Done with option 1. The sector-atomicity question (option 2) is not decided and is not part of this task: it is KV-T-0038, an open decision for the owner.**

### 2026-09-25 — option 1: a sync after the truncate

**Decision.** The owner took option 1 on 2026-09-25. Option 2 was left open: D6 was not widened, creation does not go through a temporary file and a rename, and the power-loss model still tears a meta write to a byte prefix. KV-T-0035 is completed rather than kept open, and its remainder is filed as **KV-T-0038** ("Can a sector write tear? A torn meta write during creation leaves a file that never opens"), so the backlog names the open question by its title instead of under a bug that is half fixed.

**The change.** `kv/env.odin`, `init_meta_pages`: `os_sync(fd)` after `os_truncate`, commented with the reason (a power loss must not keep a meta write while losing the sizing; a loss before that sync leaves no file, an empty one or two zero pages, all opened as new). It is one extra sync at creation, and at a D6 recreation, where the truncate is to the size the file already has. `env_open`'s doc comment now names only the case that remains: a power loss that tore a meta write with neither meta page whole, which depends on whether a sector write can tear (KV-T-0038).

**The sweeps.** Creation's journal is truncate, sync, meta 0, meta 1, sync: five operations.
- `test_crash_kill_create`: 6 cuts per page size (was 5), each opening as an empty database; it now asserts 6 cuts.
- `crash_sweep_create_power` no longer assumes one window of four operations. It cuts before each sync like `crash_sweep_power`, and takes every combination of the window's operations (a truncate taken or not; a meta write lost, whole, or torn to 1, 40 or 95 bytes), then `CRASH_SUBSETS` random subsets per window. The shape check is now "only truncates, meta writes of txn 0 and syncs, ending in a sync", and `crash_create` stopped asserting four operations, so creation without the new sync still reaches the power sweep and shows what it costs. The classification of each image is unchanged, and it counts the refused ones as `refused_torn` (two pages) and `refused_short` (the sizing lost).
- `test_crash_power_create` asserts `refused_short == 0` (the class the sync removes never occurs) and `refused_torn > 0` (the torn class is still pinned), and logs images, windows and both counts.
- `test_io_hook_per_thread` counted one sync for `env_open`: now two.

**Image counts** (fixed images only, measured with the random subsets excluded; the same at 4 KiB and 16 KiB):

| | fixed images | open | refused, torn meta (two pages) | refused, sizing lost |

| before (one window: truncate, meta 0, meta 1) | 50 | 12 | 14 | 24 |
| after (two windows: {truncate}, {meta 0, meta 1}) | 27 (2 + 25) | 13 | 14 | 0 |

With the default 16 random subsets per window, one run at seed 1234 is 66 images and 39 refused (14 torn, 25 short) before, and 59 images over 2 windows and 14 refused (all torn) after; the Linux arm64 run was 59 images, 16 refused, all torn. The images still refused are exactly the fixed ones with neither meta write whole and at least one torn to 1 (slot 1 only), 40 or 95 bytes: 4 × 4 combinations of {lost, 1, 40, 95}, less the two that leave both pages all zero (both lost, and slot 0 torn to its first byte, which is the zero low byte of `pgno`, with slot 1 lost), which D6 opens. **Correction to KV-T-0029's figures:** it reported 15 torn and 39 refused of the 50 (11 open); the count is 14 and 38 (12 open), because that one-byte tear of slot 0 writes a zero and D6 opens the image.
