# The resident estimate under-counts on Linux kernel 7.2.9

## Objective

**Triage (2026-10-17):** now — the memory budget's guarantee fails on a current Linux kernel, and Linux is the production platform

Found by KV-T-0039 (2026-10-17). On Linux kernel `7.2.9-orbstack`, the kernel reports pages of the map present that the store's resident estimate (`Stats.resident_chunks`, KV-I-0004 D7) doesn't count, and some of them are still present after `env_sweep(env, 0)`. The memory budget rests on that estimate never being under the OS's view (KV-I-0004 D8, D9), and Linux is the production platform, so this is a defect in the budget's guarantee there, not only in a test. The task is to find out what the kernel changed and to make the estimate hold again, or else to narrow what the budget claims on such kernels.

## Evidence

- **Two tests fail in every configuration** in the `scripts/test-linux.sh` image (ubuntu:24.04, arm64, OrbStack's VM on an Apple M4), and nothing else fails:
  - `-debug`: 163/165; `-o:speed`: 163/165; hooked `-debug` (`KV_IO_HOOK` + `KV_NO_SYNC`): 182/184; hooked `-o:speed`, the CI invocation: 182/184.
  - **`test_resident_check`** (`tests/resident_test.odin`): "after request 1: the OS holds 589824 bytes of the map, the estimate is 393216", then "only 2 requests without an inline eviction" and "no eviction at a transaction's end"; in other runs "after env_sweep(env, 0): the OS holds 65536 bytes of the map" (131072 in another).
  - **`test_sweep_estimate_not_under`** (`tests/evict_test.odin`, `expect_os_within_estimate`): "chunk N is present but not counted" for 11 chunks in one round (3, 4, 6, 7, 8, 10, 11, 20, 21, 23 and 28), failing in rounds 0 to 6 depending on the run.
- **It is not the compiler.** The same Dockerfile built with `--build-arg ODIN_VERSION=dev-2026-09` (`dev-2026-09-nightly:a2fb372`) gives the same counts in all four configurations and fails the same two tests and nothing else. Run alone, the two fail three runs out of three under each compiler.
- **The kernel changed.** The container's kernel is `7.2.9-orbstack`. KV-I-0004 measured and passed on `7.0.14-orbstack` (KV-T-0019, KV-T-0020, KV-T-0024), and the Linux suite last passed locally there.
- macOS arm64 passes every configuration of `scripts/test.sh` (KV-T-0039), as expected: these checks need `pagemap`, and `env_resident_check` is `.Unsupported` there.

## Leads

- **Fault-around size.** `MIN_CHUNK_SIZE` (`kv/chunks.odin`) and the chunk-aligned map (`os_map_reserve`, `kv/os_posix.odin`) assume that a fault of a shared file mapping maps a 64 KiB window, aligned by address, which stays inside one chunk (measured in KV-T-0019). A larger window, or one not bounded by the faulting chunk, would make pages resident that no read of their chunk caused, which is what "present but not counted" looks like. `/sys/kernel/mm/transparent_hugepage/enabled` is `madvise` in the container, and the OS page is 4 KiB.
- **Large folios on file mappings.** If the page cache maps a file folio larger than 4 KiB as a whole, both the fault-around window and `pagemap`'s present bits follow the folio rather than the page. It could also explain pages left after `env_sweep(env, 0)` if `MADV_DONTNEED` on part of a folio (`os_evict`, `kv/os_linux.odin`) no longer drops every page table entry in the range.
- Start by re-running KV-T-0019's measurement (`-define:KV_PLATFORM=true`, `test_platform_residency`, one thread) on this kernel and comparing it with that task's figures.

## Open question

Whether the kernel of GitHub's `ubuntu-latest` runner is affected. CI ran these two tests green on 2026-09-25 (the last run). Its next run, on whatever its kernel is then, answers that. A kernel version from `uname -r` in the workflow's "Odin version" step would make the answer readable from the log.
