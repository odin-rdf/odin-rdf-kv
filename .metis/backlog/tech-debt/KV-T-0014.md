# Place the free-list run in a fragmented free pool

## Objective

Stop the free list's own run from extending the file when there are plenty of free pages but no contiguous run of exactly the length needed.

## Backlog Item Details

### Type
- [x] Tech Debt - Code improvement or refactoring

### Priority
- [x] P2 - Medium (nice to have)

### Technical Debt Impact
- **Current problems:**
  - A run must be exactly `overflow_pages(16 × count)` long, because open validates it that way. `freelist_place` (`kv/freelist.odin`) therefore needs a free run of exactly the right length, and falls back to extending the file if there isn't one.
  - KV-T-0013 measured this: after a long reader ends, a free list of about 7,500 records (a 30-page run) extended the file 0–3 times per 1,000 commits, by 29–90 pages each time.
  - A scattered 10⁵-record list extended the file by its whole 396-page run.
- **Benefits of fixing:** the file stops growing once the free pool is large but fragmented, which completes NFR-004 for workloads that follow a long reader.
- **Risk assessment:** low for now. The growth is bounded and rare, but it gets worse as fragmentation grows, which delete (step 4) will add to.

## Acceptance Criteria

- [ ] Choose among the options with a measurement:
  - accept a run longer than its records need (relax the validation at open to `overflow_count ≥ needed`, with the slack zeroed);
  - best-fit placement, or placement from the top of the pool;
  - chain the run's pages;
  - extent records (see KV-I-0002 Alternatives).
- [ ] KV-T-0013's long-reader test runs with no file growth after the reader ends, on every seed.
- [ ] `space_check`, the validation tests and the build matrix still pass.

## Implementation Notes

The evidence is in KV-T-0013's Status Updates and KV-I-0002's Results (known limitations). Relaxing the validation is the smallest change, and it stays compatible: files written today have exact runs, which still satisfy `≥`.
