# Avoid repeated linear run searches in the ready list

## Objective

Stop paying for a full scan of `Env.free.ready` on every failed run search within one write transaction.

## Backlog Item Details

### Type
- [x] Tech Debt - Code improvement or refactoring

### Priority
- [x] P3 - Low (when time permits)

### Technical Debt Impact
- **Current problems:**
  - `ready_run_find` (`kv/write.odin`) is linear. A failed search scans the whole list: KV-T-0013 measured 70–93 µs at 10⁵ scattered records.
  - Every overflow allocation in a fragmented pool pays that cost.
  - So does `put`'s up-front `pages_available` check once the end of the map is too small.
- **Benefits of fixing:** keeps a transaction that writes many overflow values cheap when the pool is large and fragmented.
- **Risk assessment:** low. It's a cost, not a correctness issue, and it only matters with around 10⁵ free pages.

## Acceptance Criteria

- [x] Within a transaction the reusable list only shrinks, so a failed search for length `n` stays failed for every length ≥ `n`. Remember the smallest failed length in `Write_State` and skip searches at or above it.
- [x] A measurement (`tests/bench_test.odin`, `-define:KV_BENCH=true`) shows the repeated cost gone.
- [x] The build matrix passes.

## Status Updates

### 2026-09-24: done, remembering both failed searches and where runs start

**Finding: the measured cost wasn't a failed search.** I added a column to the benchmark timing a second 2-page search in the same transaction. With only the failure memo, the second search at 10⁵ scattered records still cost 114 µs against 128 µs. Logging showed why. At 10³ records and up, the scattered layout's 2-page searches **succeed**: they scan every scattered page and then find a run near the top of the file, where the first commit's free-list run (396 pages) was freed. So KV-T-0013's "70–93 µs failed search" was a long successful scan. The memo on its own does nothing for it, and the task's stated benefit (keeping a transaction that writes many overflow values cheap in a fragmented pool) depends on fixing it.

**Decision: two kinds of proof in `Write_State`, both resting on the task's argument that the list only shrinks during a transaction.**
- **Failures (as the acceptance criterion asks):** `miss` is the shortest length a search skipping nothing failed for. `miss_skipped`/`miss_skip` record the same for put's up-front check, which skips the lowest untaken pages. A failure at (n, s) implies failure at every (n' ≥ n, s' ≥ s): the untaken pages left after skipping s are a superset of those left after skipping more, or after more pages are taken. A failure skipping nothing covers every skip.
- **Where runs start (beyond the criterion):** a search skipping nothing that finds a run of n at index i proves that no run of n or more starts before i. Later searches for n or more start there. `run_from[n]` covers n = 2..`RUN_HINTS` (8), and longer lengths use the largest entry at or below them. This is `ready_next` generalized from single pages to runs. The scan was split out as `ready_run_scan`, which takes a start index.
- **Skipping searches neither record nor use `run_from`:** their skip counts untaken pages from `ready_next`, and a run found after skipped pages says nothing about the pages skipped.

**Tests:**
- `test_page_alloc_matches_a_direct_search`: 20 random pools with density 0.2–0.8, 200 allocations of 1–6 pages each, compared with a direct lowest-first search in the test.
- `test_put_refused_for_a_run_leaves_shorter_runs`: at a full map, a refused 3-page put blocks neither a 2-page put nor a `page_alloc(3)` that skips nothing.
- `test_put_run_is_lowest_after_the_path`: the check finds a run after the pages it sets aside, and the value still goes to the lowest run left once the path has taken one page.
- `test_put_check_counts_from_the_lowest_page`: after a 2-page run was found above page 2, the check still counts its skip from page 2.

**Checked against deliberate bugs, each caught:**
- memo blocking one length shorter (`n + 1 >= miss`): the randomized test, on its own too;
- the skipped memo blocking one length shorter: the refused-put test;
- the skipped memo applied whatever the skip, or skipped failures recorded as unskipped: the refused-put test (`page_alloc(3)` gets `Map_Full`, want 2);
- a longer length's start used for a shorter run: the randomized and lowest-first tests;
- a hint recorded by a skipping search: `test_put_run_is_lowest_after_the_path` (dirty pages [2, 10, 11, 12], want [2, 3, 4, 5]);
- a hint applied to a skipping search: `test_put_check_counts_from_the_lowest_page`.

Not a bug: recording `idx + 1` instead of `idx`. The pages of the run just found are taken, so no run starts at them either.

**Measurement** (`-define:KV_BENCH=true`, macOS arm64, `-o:speed`, medians over 40 aborted transactions, on a quiet machine). The benchmark has a new "again" column, a second 2-page search in the same transaction, and a 1,024-page search timed twice, which fails in the scattered layout (`NO_RUN`). Before is `main` with only the new benchmark:

| Free list | 2-page search | again | 1,024-page | again |
|---|---|---|---|---|
| Scattered 10⁴, before | 11.1 µs | 12.0 µs | 16.1 µs | 15.0 µs |
| Scattered 10⁴, after | 11.6 µs | **0.71 µs** | **6.2 µs** | **4.9 µs** |
| Scattered 10⁵, before | 96.8 µs | 121 µs | 127 µs | 122 µs |
| Scattered 10⁵, after | 92.8 µs | **0.58 µs** | **6.4 µs** | **3.6 µs** |

- **The repeated cost is gone.** Only the first search in a transaction still scans the scattered part of the list.
- The first 1,024-page search is cheap as well, because it starts where the 2-page search found its run.
- The ~4–6 µs left on the 1,024-page searches is the 4 MiB buffer allocated at the end of the file. The Runs layout pays it too, at 5–10 µs before and after.
- Every other column is unchanged within noise.
- `scripts/test.sh --steady`: 112/112 in debug, `-o:speed` and ASan, and `odin check` is clean for the four targets. In each long-reader run the file didn't grow after the reader ended.
