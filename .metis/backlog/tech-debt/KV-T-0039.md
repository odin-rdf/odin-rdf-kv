# CI tracks the latest Odin; the Linux image builds with dev-2026-10

## Objective

The family's development machines are moving to Odin `dev-2026-10` (`odin version` reports `dev-2026-10:84bc3fc21`). This repository pinned the compiler in two places, `.github/workflows/ci.yml` (`release: dev-2026-09`) and `scripts/linux.Dockerfile` (`ARG ODIN_VERSION=dev-2026-09`), and the workflow's comment asked for those two and the development machine to move together.

Every other library in the family (odin-rdf-parser, -record, -shacl, -sparql) runs `laytan/setup-odin@v2` with `release: latest` in CI, and as of 2026-10-17 that is the family's rule for every library: a library tracks the newest compiler so that a breaking Odin release shows up in its own CI first, before a consumer building with that compiler finds it. This repository was the exception and joins them. The Linux container stays pinned, because its download URL needs a concrete version, and it follows the development machine's compiler.

The release exists (published 2026-10-06) and carries the asset the Dockerfile downloads, `odin-linux-arm64-dev-2026-10.tar.gz`, as well as `odin-linux-amd64-dev-2026-10.tar.gz` for `scripts/test-linux.sh amd64`.

## Acceptance Criteria

- [x] `.github/workflows/ci.yml` runs `release: latest`, and the comment above it says why (the family's libraries track the newest compiler so a breaking release shows up in their own CI first).
- [x] `scripts/linux.Dockerfile` defaults `ODIN_VERSION=dev-2026-10`, and its comment keeps the rule of matching `odin version` on the development machine.
- [x] The coupling of CI with the Dockerfile and the development machine ("bump all three together") is stated nowhere current.
- [x] Every other mention of `dev-2026-09` that states the current pin is updated: `CLAUDE.md`'s Linux-tests note, `README.md`'s toolchain line, and `vision.md`'s Current State (by a dated amendment, the old text standing). Mentions that record what was true at the time (archived tasks and initiatives, and the compiler the pitfalls were hit on) stay as written.
- [x] `scripts/test.sh` passes on macOS arm64 with `dev-2026-10`, including the cross-target `odin check`s the workflow runs.
- [x] The Linux suite (`scripts/test-linux.sh arm64`'s four configurations) gives the same result in a container built with `dev-2026-10` as in one built with `dev-2026-09`: everything passes but `test_resident_check` and `test_sweep_estimate_not_under`, which fail under both on the container's kernel, `7.2.9-orbstack`. That failure is **KV-T-0040**. *(Amended 2026-10-17: this read "`scripts/test-linux.sh arm64` passes in a container built with `dev-2026-10`", which a kernel change made unmeetable by any compiler bump. The criterion now says what a compiler bump can show.)*

**2026-10-17, Linux.** `scripts/test-linux.sh arm64` built the image with `dev-2026-10` (in the container `odin version` prints `dev-2026-10-nightly:84bc3fc`, the same commit as the development machine) and failed its first configuration: 165 tests, 163 pass, **`test_resident_check`** ("no eviction at a transaction's end", or "after env_sweep(env, 0): the OS holds 65536 bytes of the map") and **`test_sweep_estimate_not_under`** ("chunk N is present but not counted") fail. The other three configurations, run directly in the same image, show the same two and nothing else: `-o:speed` 163/165, hooked `-debug` 182/184, hooked `-o:speed` (the CI invocation) 182/184.

**It is not the compiler.** The same image built with `--build-arg ODIN_VERSION=dev-2026-09` fails the same two tests, three runs out of three, as `dev-2026-10` does. What changed is the environment: OrbStack's kernel is `7.2.9-orbstack` today, where KV-I-0004 measured and passed on `7.0.14-orbstack`, and CI (`ubuntu-latest`) was last green on 2026-09-25. Both tests compare the store's resident estimate with the kernel's `pagemap`, so the kernel now reports map pages present that the estimate didn't count, or kept them after `env_sweep(env, 0)`. That is a finding about the store on newer Linux kernels, filed as KV-T-0040, not fixed here. OrbStack started for the runs and stopped afterwards.
