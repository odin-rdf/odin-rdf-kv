# OS residency check and the memory-budget criterion

## Parent Initiative

[[KV-I-0004]]

## Objective

Check the estimate against the OS (KV-I-0004 D10) and show the vision's success criterion: with a database of about 100 MB and a 20 MB budget, the resident footprint stays within about 1–2 chunks of the budget under mixed load, on macOS and Linux. Then close the initiative: measurements, vision, `CLAUDE.md` and Results.

## Acceptance Criteria

- [ ] **`env_resident_check(env) -> (resident_bytes: int, err: Error)`:** counts the map's pages present in the process over the file's extent. Linux: `/proc/self/pagemap` present bits, never `mincore` (it reports the page cache). **macOS: returns `(0, .Unsupported)`**, a new `Error` value added by this task (KV-T-0019 found no macOS source that counts a range's pages mapped into the process: `mincore` and `mach_vm_region` both report the page cache; D10 as amended 2026-09-24). It doesn't change the estimate (Q4).
- [ ] Tests (Linux): after reads, the check is at most the estimate plus a small tolerance; after `env_sweep(env, 0)`, it is near 0. On macOS, a test that the check returns `.Unsupported`, and the same two checks made against the process's `task_info` `resident_size` above a baseline taken after `env_open` (after `env_sweep(env, 0)` it is back near the baseline).
- [ ] **The criterion test**, on demand (a define, like the steady tests): a database of about 100 MB; `mapped_budget` about 15 MB and the default 4 MiB dirty pool; reader, scanner and writer threads, with **no `env_sweep` calls**: the budget is held by the check at the end of every transaction and by inline eviction (KV-I-0004 D8/D9 as amended 2026-09-24). Report how many evictions each path made. Sample the resident figure plus `dirty_committed` throughout and assert they stay within 2 chunks of the total budget. **Linux:** the resident figure is `env_resident_check`. **macOS:** it is the process's `task_info` `resident_size` above a baseline taken right after `env_open` (the test process holds nothing else of size; allow for the test's own allocations in the tolerance, and record it). Run on macOS and Linux (arm64, amd64); KV-T-0019 showed macOS eviction (the `MAP_FIXED` remap) is effective, so both assert.
- [ ] The drift between the estimate and the OS figure (`pagemap` on Linux, `resident_size` above the baseline on macOS) is reported (Q4 decides nothing is corrected unless it's large).
- [ ] **Measurements, recorded in this task and the initiative's Results:** the time the end-of-transaction check adds (under budget; when it evicts) and the time `env_sweep(env, 0)` takes to put a store to sleep; the memory left after `env_sweep(env, 0)` against after `env_close`; the time `env_open` takes to wake a store, with a short and a long free list.
- [ ] **Capacity-planning figures** for the first deployment (the user's hardware sheet), measured from the OS, per store, in the same form as the design bound `mapped_budget + 2 × chunk_size + dirty_budget + fixed`. A table on Linux (the production platform) and macOS, for at least two settings (the default 256 KiB chunks with a 15 MB budget, and 64 KiB chunks with an 8 MiB budget):
  - **active, worst case:** the peak resident figure plus the peak dirty pool under the criterion test's mixed load, against the design bound;
  - **active, typical:** resident and dirty figures under a light request-like load (single-entry reads and writes of conversation-sized values, a few per second), after it settles;
  - **asleep:** after `env_sweep(env, 0)`, what the store still holds: the resident figure, `free_list_bytes`, the chunk table and the fixed structures, against the same after `env_close`;
  - **fixed structures** broken down: chunk table, reader table, `Env`, free list, pool bookkeeping;
  - reserved address space (`map_size` + `dirty_budget`) stated separately as virtual, not RAM.
  The table goes in this task's Status Update and in KV-I-0004's Results, with the method used for each figure.
- [ ] The full matrix passes on macOS and Linux. The steady-state tests run once each, debug only, with `-define:KV_STEADY_COMMITS=1000` (the user avoids the full-length runs for their CPU use); record that the full `scripts/test.sh --steady` was skipped.
- [ ] Documentation:
  - the vision's Current State, and its memory-budget section amended: no sweeper thread; the store checks its budget at the end of every transaction and evicts inline as a backstop; the application calls `env_sweep(env, 0)` to put an idle store to sleep (a dated note, the old text standing);
  - step 7's scope gains "killed after a spill, before commit";
  - `CLAUDE.md`: the new options, `env_sweep`, the test defines, and the code map;
  - KV-I-0004's Results: the exit-criteria table, deviations and known limitations, as KV-I-0003 has.

## Implementation Notes

### Technical Approach
- Read `/proc/self/pagemap` in batches over the file's pages only (8 bytes a page: 200 KiB for a 100 MB file).
- The 100 MB database is built once per run in a temporary directory with the bulk of values in the few-hundred-byte range and some overflow values, like conversation messages.

### Dependencies
KV-T-0021, KV-T-0022 and KV-T-0023. Last task of KV-I-0004.

### Risk Considerations
- The criterion test is timing-dependent; it asserts on samples of the resident figure, not on throughput, so a slow CI machine only makes it slower.
