# Power-loss images: lost, torn and reordered writes

## Parent Initiative

[[KV-I-0005]]

## Objective

Show the stronger claim, crash safety from ordering and checksums: after a power loss, when writes since the last sync may be lost, torn or reordered, the database still reopens at a state it is allowed to be in (KV-I-0005 D2).

## Acceptance Criteria

- [ ] `journal_image_power(baseline, journal, n, subset, tears, path)`: the baseline, every operation up to the last sync before `n`, then only the chosen later operations, each write whole or torn to a subset of its 512-byte sectors; a truncate outside the subset leaves the size as it was.
- [ ] Per cut, fixed images: none of the later operations; all of them; only the meta-page write; the meta-page write torn. Then `KV_CRASH_SUBSETS` random subsets with random tears (default 4), from the test's seed, which failure messages carry with the cut and the subset.
- [ ] Allowed states: the last commit whose second sync precedes the cut, or the successor's if its meta-page write is in the image whole. A torn meta page must be rejected by its checksum and the other slot used. Every image also passes `tree_check`, `space_check`, one more commit and a reopen.
- [ ] Run over workloads 1–4 from KV-T-0027.
- [ ] Deliberate-bug checks recorded, each failing: skip the meta checksum check in `meta_choose`; drop the first sync (now visible as a durable meta page over lost data pages, where the kill sweep may not see it); take the meta page with the *lower* `txn_id`. *(Note from KV-T-0027, 2026-09-25: two more of the bugs KV-T-0027 was given turned out to be invisible to a kill image and belong here: writing the meta page into the **current** slot (`(txn_id − 1) & 1`), which a torn meta write should expose as a fall-back to a stale slot; and a reuse horizon of S instead of S − 1, which only matters when the newest meta page is unreadable, and may need a meta-corruption image rather than a power-loss one to show.)*
- [ ] `scripts/test.sh` and `scripts/test-linux.sh arm64` pass.

## Implementation Notes

### Technical Approach
- Reordering needs no separate model: a subset of unsynced writes applied in any order produces the same bytes unless two writes overlap, so overlapping writes are applied in journal order and the subset choice covers reordering.
- The simulation assumes a sync that returned made everything before it durable, the contract the store is written against (KV-I-0005 non-goals).
