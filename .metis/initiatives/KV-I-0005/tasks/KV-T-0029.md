# Recreate a new file with nothing written

## Parent Initiative

[[KV-I-0005]]

## Objective

A crash while creating a database must not leave a file that can never be opened (KV-I-0005 D6), and the sweep must cover creation (workload 5).

## Acceptance Criteria

- [x] `env_open`: when `meta_choose` finds no valid meta page, the file is exactly `2 × page_size` (the page size this open would use) and every byte of it is zero, initialise it as a new database. Anything else without a valid meta page stays `.Corrupted`.
- [x] The doc comment of `env_open` states the rule.
- [x] Workload 5 of the design, `env_open` of a new path, swept with kill and power-loss images: each opens as an empty database, or with one valid meta page, never `.Corrupted`.
  - *Amended 2026-09-25: true of every kill image, not of every power-loss image.* Under the power-loss model a creation can leave a file with no valid meta page that isn't all zero: a meta write torn (to a byte prefix) with no whole one beside it, or a meta write kept while the truncate was lost (a 96-byte file, or one page and a meta prefix). The narrow D6 rule refuses those as `.Corrupted`, by design. The sweep **pins** that (each such image must be `.Corrupted`, and both kinds must occur) and counts them; whether they should open is a design question for the owner, see the status update. The rule was not widened.
- [x] Tests: a 2-page zero file opens as empty and takes a commit; a 2-page file with one nonzero byte, a 3-page zero file and a zero file at another page size return `.Corrupted`.
- [x] Deliberate-bug checks recorded: accept any all-zero file regardless of size (the 3-page test fails); remove the rule (the workload 5 sweep fails).
- [x] `scripts/test.sh` and `scripts/test-linux.sh arm64` pass.

## Status Updates

### 2026-09-25 — implemented and verified; one design question for the owner

**What was built.**
- `kv/env.odin`, `env_open`: after `meta_choose` finds no valid meta page, if the file is exactly `2 × page_size` (the page size of this open: `Options.page_size` or `DEFAULT_PAGE_SIZE`) and `mem.check_zero` of the mapped file is true, `init_meta_pages(fd, page_size)` writes the two meta pages (the truncate is to the size the file already has) and syncs, and `meta_choose` runs again over the same shared map. Otherwise `.Corrupted`, as before, **and the file is not touched**. `chunk_touch(e, 0)` moved before `meta_choose`, since the zero check reads the map too (both pages are in chunk 0). The doc comment states the rule and names the images it does not cover.
- `tests/env_test.odin`: `test_env_new_file_all_zero` (a two-page zero file at 4096, and at 16384 opened with that page size, opens at txn 0, takes a commit, reopens with it); `test_env_new_file_rule_is_narrow` (each must be `.Corrupted` **and left byte for byte as it was**: two pages with one nonzero byte at 8191, 4095, 16 (slot 0's magic) and 4115 (inside slot 1's prefix); three zero pages; one zero page; `2 × 8192` zeros opened at the default page size; `2 × 4096` zeros opened at 8192; and slot 0 holding the first 40 bytes of a real meta page with slot 1 zero — the torn creation).
- `tests/crash_sweep_test.odin`: workload 5, `crash_workload_create` and `crash_workload_create_16k` (baseline of no file, `states[0]` the empty model at txn 0, the journal of one `env_open`, asserted to be four operations). `test_crash_kill_create` runs both through the existing `crash_sweep_kill` unchanged (and asserts one cut after a truncate); `test_crash_power_create` through the new `crash_sweep_create_power`.
- `tests/crash.odin`: `crash_sweep_create_power` and `crash_create_image`. The commit power sweep doesn't fit creation (no synced state before the window, and its meta pages are txn 0, not the successor), so creation has its own: it asserts the journal is truncate, meta 0, meta 1, sync, then takes **every** combination of the truncate taken or not and each meta write lost, whole, or torn to a prefix of 1, 40 (`POWER_META_TORN`) or 95 bytes — 2 × 5 × 5 = 50 images — plus `CRASH_SUBSETS` random ones from `power_random`. Each image is classified by its bytes: no file, two zero pages, or two pages with a meta write whole must pass `crash_image_check` at txn 0; anything else must be `.Corrupted`, counted as `refused_torn` (two pages long) or `refused_short` (the truncate lost). `Crash_Run.options` is new: `crash_image_check` opens with it (zero for workloads 1–4, the page size for creation, since D6 is at the page size of the open).
- Two fixes in the test driver found on the way: `crash_finish` sized `value_buf` by the largest workload value only, so a workload with no values panicked in the extra commit's 64-byte value; now `max(max_value, CRASH_EXTRA.size)`. `crash_state` compared `int(txn_id − base_txn)` against `len(states)`, which for `txn_id = S − 1` with `S = 0` wraps to −1 and indexes out of range; now compared unsigned. Neither affected workloads 1–4.

**What a torn creation leaves, and how each opens.** Creation is: truncate to two pages, meta 0 (96 bytes at 0), meta 1 (96 bytes at `page_size`), sync.
- Process kill (every cut): no file or an empty one (new, as before); two zero pages (**D6: recreated**); meta 0 whole, slot 1 zero (opens from slot 0); both (opens). All five cuts at each page size open at txn 0 and pass the image check.
- Power loss, truncate taken: neither meta write present → two zero pages → D6. One whole, the other lost or torn → opens from the whole one (`meta_choose` probes page sizes when slot 0 is bad). **Neither whole and at least one torn → `.Corrupted`** (15 of the 50 fixed images).
- Power loss, truncate lost: no meta write → empty file → new. **Any meta write present, whole or torn → `.Corrupted`**: the file is 96 bytes, `page_size + 96`, or a torn prefix, and no meta page can be valid in a file shorter than the page it describes (24 of the 50).
- Why refusing them is right *under D6 as decided*: such a file is neither all zero nor holds a valid meta page, and D6 says exactly that anything else stays `.Corrupted`, so no damaged database is quietly replaced. `test_env_both_metas_corrupt` (a two-page database with both checksums bad) is the case the narrow rule is protecting, and it still fails to open.

**Design question for the owner (not decided here, the rule was not widened).** A power loss during creation can leave a file that can never be opened, which is what D6 set out to prevent; D6 covers the kill model fully and the power-loss model only partly. The two classes and the ways out:
1. *Truncate lost, meta write kept* (the file shorter than two pages). **A sync after the truncate in `init_meta_pages`** removes this class entirely: the window is then only the two meta writes over a durable two-page zero file. One extra sync, only at creation. (Tried: the sweep's shape assertion stops it, as intended, so the counts need the sweep adapted if taken.) Whether a real file system can persist an extending `pwrite` while losing an earlier `ftruncate` is file-system specific; the model allows it, as it does for commits.
2. *A meta write torn with no whole one beside it.* Only a tear inside a 96-byte write, i.e. inside one 512-byte sector, produces it. With (1), **sector-atomic writes** (the assumption LMDB and most of the storage stack make, and stricter hardware than the model's byte-prefix tear) make every creation image open. Without that assumption no in-place creation can avoid it; the options are (a) widen D6 to "no valid meta page, at most two pages at this page size, every nonzero byte inside the two meta-page prefixes" — safe in the sense that a file of two pages holds no data page, but it is a heuristic over damaged bytes; or (b) create at a temporary path and `rename` it into place (with a directory sync), which the journal doesn't model and which changes how `env_open` treats an existing empty file.
Recommendation: (1) now, and decide (2) by whether the power-loss model's sub-sector tear is meant to bind creation.

**Measured** (debug, `KV_IO_HOOK` + `KV_NO_SYNC`, macOS arm64, inside `scripts/test.sh`): kill 5 cuts per page size, 7 ms and 4 ms; power 66 images per page size (44 refused, 18 torn and 26 short in that run, the random ones varying by seed), 22 ms and 21 ms. **About 55 ms in all.** Linux arm64 container: kill 2.5 ms each, power 66 images each (43 refused). `-define:KV_CRASH_SUBSETS=500`: 550 images per page size, about 0.25 s, all as classified, over five seeds.

**Deliberate-bug checks** (the two env tests, the two create sweeps, `test_env_both_metas_corrupt` and `test_env_truncated_file`, `-debug -define:KV_IO_HOOK=true -define:KV_NO_SYNC=true -define:ODIN_TEST_THREADS=2`, under `timeout -s KILL 300`; `kv/env.odin` restored from a saved copy after each and checked with `cmp`):
1. Accept any all-zero file regardless of size (`!found && mem.check_zero(...)`): `test_env_new_file_rule_is_narrow` fails — "12288 zero bytes opened at page size 0: env_open returned None, want Corrupted" (the 3-page file), and the `2 × 8192` file at the default page size; the one-page file is refused but rewritten ("the refused file was changed").
2. Remove the rule (`if false`): `test_crash_kill_create` fails ("create, kill at cut 1 of 4, after Truncate to 8192: env_open: Corrupted", and the 16k one), `test_crash_power_create` (subset 0, the truncate alone) and `test_env_new_file_all_zero` fail.
3. Drop the zero check (size alone): `test_crash_power_create` fails ("subset 0 2, tears 2 kept [0:1]: env_open: None, want Corrupted" — the pin on torn creation), `test_env_both_metas_corrupt` fails (a damaged database replaced by an empty one), and `test_env_new_file_rule_is_narrow` on every nonzero-byte case and the torn slot.
4. Compare with `DEFAULT_PAGE_SIZE` instead of this open's page size: the 16k kill and power sweeps, `test_env_new_file_all_zero` at 16384 and the narrow test's "2 × 4096 at 8192" case fail.

**Deviations.** Criterion 3 amended (above): the power-loss images that D6 refuses are pinned as `.Corrupted` and reported, not made to open. The sweep also runs at a 16 KiB page size, beyond the criterion, because the rule is page-size dependent. No store bug found beyond the design question.
